# v4.1.0 – Action Deduplication + UI IDs

## Goal

Prevent duplicate ITSM tickets when Jira fires update events for the same issue. Actions gain an optional deduplication expression; the dispatcher updates an existing ticket instead of creating a new one when a match is found.

## In Scope

* `Action.dedup_expression` — optional JSONPath field; if set, the dispatcher resolves it against the payload to obtain a unique key
* `Ticket.external_id` — blank, db-indexed CharField; stores the resolved dedup key on create
* Dispatcher update path: if dedup key matches an existing ticket, re-apply `field_mappings` and log field changes via `TicketEvent`; state and `assigned_to` are not touched
* `TriggerLog.result` reflects `matched` on update (same as create)
* Action and Trigger list templates: display pk as a muted label beside each row

## Out of Scope

* Cross-action deduplication
* Merging existing duplicate tickets
* State or assignment changes on update
* Dedup for sources other than Jira

## Acceptance Criteria

* Action form exposes `dedup_expression` field with placeholder `$.issue.key`
* First webhook for GIT-123 creates one ticket with `external_id="GIT-123"`
* Second webhook for GIT-123 updates that ticket's mapped fields, no new ticket created
* Field changes on update are logged as `TicketEvent` entries
* Actions without `dedup_expression` continue to always create
* Action and Trigger list rows display their pk

## Validation Plan

* Set `dedup_expression = $.issue.key` on an action, fire two payloads with the same key — verify one ticket exists after both
* Fire two payloads with different keys — verify two tickets exist
* Leave `dedup_expression` blank — verify create-only behaviour unchanged
* Check Log tab on updated ticket shows field change entries
