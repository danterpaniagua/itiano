# Goal

Move `Team` from `vault` to `core` (where `UserProfile` already lives) so it's an app-wide concept by location, not just by aspiration — even though `vault` remains its only real consumer today. This is a pure Django-organization change: no behavior change, no new functionality. Must not disturb the crypto foundation `v5.10.0`/`v5.10.1` already shipped on `main`.

**Safety-first design decision**: keep the physical database tables exactly as they are (`vault_team`, `vault_team_members`) via explicit `db_table` overrides on the relocated model. This is a **state-only** move — Django's bookkeeping of which app "owns" the model changes, but zero data moves, zero tables are renamed, zero physical DDL touches the tables that hold real encrypted credential data. A real table rename (`vault_team` → `core_team`) would be low-risk on its own, but combined with three already-shipped scopes' worth of FK dependents and crypto signal wiring, minimizing moving parts wins over naming purity here. Can be revisited later as a separate, purely cosmetic cleanup if ever wanted.

# In Scope

- `Team` model moves from `vault/models.py` to `core/models.py`, unchanged (including the `save()` auto-`code`-generation override from `v5.10.0`/`v5.10.1`'s Delivery Note).
- `Team.members` M2M keeps `related_name='vault_teams'` and its physical join table name (`vault_team_members`) — not renamed, to avoid touching every `vault_teams` reference across `crypto.py` for a purely cosmetic gain.
- `vault.TeamKeyWrap.team`, `vault.ContainerAccess.team`, `vault.Credential.team` — FK target changes from local `Team` to `core.Team`.
- Every `from .models import Team` (or `Team` via local `models` import) across `vault/crypto.py`, `vault/signals.py`, `vault/forms.py`, `vault/admin.py` → `from core.models import Team`.
- `vault/signals.py`'s `m2m_changed` sender string: `'vault.Team_members'` → `'core.Team_members'` (the through-table's app_label follows wherever the declaring model — `Team` — now lives).
- `TeamAdmin` moves from `vault/admin.py` to `core/admin.py`, alongside the model.
- Migrations in both `core` and `vault` using `SeparateDatabaseAndState` with empty `database_operations` for the model move itself (state-only, see above) — verify via `sqlmigrate` that the FK-repoint `AlterField` operations on `TeamKeyWrap`/`ContainerAccess`/`Credential` produce no destructive SQL before applying.

# Out of Scope

- Any physical table/column rename — deliberately avoided, see design decision above.
- Renaming `related_name='vault_teams'` to something more generic (e.g. `teams`) — cosmetic, not required for the app-wide goal, would touch every `get_container_members`/`_visible_credentials` query unnecessarily.
- Any new functionality using `Team` outside `vault` — this scope only relocates the model; actually using it elsewhere is a future concern, not this one.
- The settings UI (`v5.10.5`), tree UI (`v5.10.6`), KDBX merge (`v5.10.7`) — this scope blocks all three (they need to know where `Team` lives) but doesn't touch any of them.

# Delivery Note

The relocation itself went exactly as designed (every migration operation a database no-op, zero physical risk). But it accidentally exposed two **pre-existing, latent bugs in `v5.10.0`'s and `v5.10.1`'s own migrations** (`0004_team_code_team_description_teamkeywrap.py`, `0005_container_credential_container_containeraccess_and_more.py`) that had been sitting there undetected since those scopes shipped:

Both `RunPython` functions did a **live** `from vault.models import Credential, Team` (0004) / `from vault.models import Container, ContainerAccess, Credential, Team` (0005) instead of `apps.get_model(...)` (the historical, migration-state-correct model). This is wrong for two independent reasons, only one of which is specific to this relocation:

1. **Specific to this move**: once `Team` left `vault.models` entirely, the live import raised `ImportError` immediately — impossible to miss.
2. **Pre-existing, unrelated to the move**: even before Team relocated, live-importing `Credential` in migration `0004` was already subtly wrong — `Credential`'s live shape (as of `v5.10.3`) includes fields (`is_deleted`, `encrypted_notes`, `container`, etc.) that migrations `0005`/`0006`/`0007` add *after* `0004` runs. On a fresh migration replay, by the time `0004`'s `RunPython` executes, those columns don't exist in the database yet — a live model reflects the *final* schema, not the schema at that point in history. The specific queries in `0004`/`0005` happened not to reference those columns, so this particular manifestation was silent — but it was one field-set mismatch away from a hard SQL error, and represents the same fragility as the `ImportError` did.

Both were **only ever exercised via `manage.py migrate` against the persistently-running dev DB**, which applies migrations incrementally as they're written and never replays history from scratch. `manage.py test` (which builds a fresh test database, replaying every migration from `0001`) is what actually caught both — this is the first point in the entire `v5.10.x` arc where a genuine from-scratch replay happened. Fixed both functions to use `apps.get_model` throughout, with live re-fetches (by `pk`) only for objects passed into `vault.crypto` functions (which do need live-typed instances — `TeamKeyWrap`/`ContainerKeyWrap` query against the *current* FK target model, which historical instances fail Django's type check against). Also hardcoded string literals (`'team'`, `'read_write'`) instead of class constants (`Credential.VIS_TEAM`, `ContainerAccess.ACCESS_READ_WRITE`) in the fixed functions, since historical `apps.get_model` classes don't carry custom class attributes, only fields.

**Lesson for any future Vault migration with a `RunPython` step**: always use `apps.get_model` for querying/updating, always re-fetch by `pk` into a live-imported class before passing into any `vault.crypto` function, and run `manage.py test` (not just `manage.py migrate` against the dev DB) before considering a migration validated — incremental application against a long-lived dev DB will never catch this class of bug.
