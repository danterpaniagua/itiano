# Goal

`v5.12.0` shipped a reconciliation crawler that backfills missing **status transitions**
for tickets already known to the app. It deliberately left three gaps: ticket body
fields (title, assignee, labels, etc.) are never refreshed by the crawler, non-status
changelog changes are ignored, and comments are never backfilled at all.

This scope closes two of those three gaps: a ticket that missed a lot of activity
during downtime should come back fully current — status, body fields, and comments —
after the next reconciliation run.

# In Scope

- `jira_reconcile` fetches `GET /rest/api/3/issue/{key}` (plain snapshot, no expand)
  for every scanned ticket and refreshes `JiraTicket` body fields — title,
  project_key, issue_type, assignee, assignee_account_id, labels, parent_key —
  using the exact same field-mapping/truncation rules the webhook already applies.
  Status is **not** touched by this snapshot refresh — it remains governed
  exclusively by the changelog path from `v5.12.0` (never overwritten from
  snapshot), consistent with the changelog-is-source-of-truth rule in
  `.claude/feature_jira_workflow.md`.
- Refactor: extract the field-mapping block currently inline in
  `jira_integration/views.py:webhook()` into a shared function
  `_ticket_defaults_from_fields(fields)` in `jira_integration/views.py` (or a new
  `jira_integration/sync.py` if that reads cleaner once written), used by both
  `webhook()` and the new crawler code. This is required, not incidental — without
  it the mapping logic would exist in two places and drift.
- `jira_reconcile` fetches `GET /rest/api/3/issue/{key}/comment` (paginated) for
  every scanned ticket and inserts a `JiraEvent(event_type='jira:issue_commented')`
  for any comment not already recorded, deduped by Jira's comment `id` stored at
  `payload['comment']['id']` — mirroring the existing changelog-history dedup
  pattern. Summary text reuses the existing `_build_summary()` comment branch.
- Per-ticket log line (`jira_reconcile_issue_done`) extended with `status_events`,
  `comments_created`, and `body_refreshed` (bool) fields, on top of the existing
  `outcome`/`events_created`.
- `stats` dict in the run summary log gains a `comments_created` counter alongside
  `events_created`.

# Out of Scope

- Comment edits/deletions — only backfills comments that currently exist server-side
  and aren't yet recorded; an edited-during-downtime comment is stored with its
  first-seen body, not its latest edit.
- Discrete `JiraEvent` history entries for non-status field changes (e.g. an
  "assignee changed" audit event) — the body refresh corrects end state only, it
  does not reconstruct a full change history for non-status fields.
- Backfilling tickets never seen by the webhook (still skipped/logged as
  `jira_reconcile_unknown_ticket_skipped`, unchanged from `v5.12.0`).
- Any UI to browse backfilled comments differently from live ones — they render
  through the existing ticket detail/timeline views identically.

# Technical Changes

- `jira_integration/views.py` — extract `_ticket_defaults_from_fields(fields)`;
  `webhook()` calls it instead of inline field mapping.
- `jira_integration/management/commands/jira_reconcile.py`:
  - `_reconcile_issue()` fetches the issue snapshot once and reuses it for both
    the body refresh and (unchanged) status/changelog handling.
  - New `_iter_comments(session, base_url, issue_key)` — paginated comment fetch.
  - New comment-dedup + `JiraEvent` insert logic.
  - Extended stats/logging as described above.
- `jira_integration/tests.py` — new coverage: body fields refresh from snapshot,
  no status overwrite from snapshot refresh, comment backfill + dedup on rerun,
  webhook behavior unchanged after the extraction refactor.
- `.claude/feature_jira_workflow.md` — update the "Reconciliation Crawler" section
  to describe the expanded scope (body + comments), and note the shared
  `_ticket_defaults_from_fields` helper in Implementation Notes.

# Acceptance Criteria

- Running `jira_reconcile` on a ticket whose title/assignee/labels changed in
  Jira while the app was down updates `JiraTicket` to match Jira's current state.
- Running it twice produces no duplicate comment `JiraEvent`s (idempotent, same
  guarantee as the status path).
- A ticket's `status` is never changed by the body-refresh snapshot fetch — only
  by the existing changelog path.
- Comments posted while the app was down appear as `JiraEvent` rows after one
  reconcile run, visible in the ticket's event history the same way a live
  webhook-sourced comment would be.
- All existing `jira_integration` tests continue to pass unchanged in behavior
  (the webhook refactor must be behavior-preserving).
- New tests for body refresh and comment backfill pass.
