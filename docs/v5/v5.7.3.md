# v5.7.3 — Trigger Identity Tag

## Goal

Allow a Trigger to carry a single static ITSM Tag that identifies which automation
created a ticket. When the trigger fires, that tag is stamped onto the ticket as
`TicketTag(source='automation')`, alongside any dynamic tags from the Action's
`tag_expressions`.

## In Scope

- Add `tag` ForeignKey (nullable, SET_NULL) to `Trigger` referencing `itsm.Tag`
- Migration
- `tag_name` text input on the trigger form — pre-filled with the current tag name on edit
- Saving sets or clears `trigger.tag` via `get_or_create`
- Dispatcher: merge trigger static tag with action dynamic tags before stamping ticket

## Out of Scope

- Multiple tags per trigger
- Tracking tag changes in TriggerHistory
- Removing dynamic tags from Actions

## Technical Changes

- `automations/models.py` — `tag` FK on `Trigger`
- `automations/migrations/0009_trigger_tags.py`
- `automations/forms.py` — `tag_name` CharField (non-model), pre-filled from `instance.tag.name`
- `automations/views.py` — `_save_trigger_tag()` helper; called in create and edit after `form.save()`
- `automations/dispatcher.py` — `trigger.tag_id` check; passes `(tag.name, tag.color)` to `_upsert_tags`
- `automations/templates/automations/trigger_form.html` — `tag_name` renders inline via generic field loop

## Acceptance Criteria

- Trigger form shows a "Trigger Tag" text input
- Typing a tag name and saving creates the tag and links it to the trigger
- Reopening the trigger shows the tag name pre-filled
- Clearing the field and saving removes the tag from the trigger
- When the trigger fires, the tag is stamped on the created/updated ticket
- Dynamic tags from `Action.tag_expressions` still apply
- Triggers with no tag behave as before

## Validation Plan

- Open a trigger edit page — Trigger Tag field must be visible
- Type a tag name, save, reopen — field must be pre-filled with that name
- Resend a Jira event that matches the trigger — resulting ticket must carry the tag
