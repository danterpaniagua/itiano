# Goal

Stop hard-deleting `vault.Credential` rows. Deletion becomes a soft delete (`is_deleted` flag, matching the existing `jira_integration.JiraTicket.is_deleted` pattern), and every delete/restore produces a `CredentialVersion` changelog entry via the existing versioning mechanism.

# In Scope

- `Credential.is_deleted = models.BooleanField(default=False)`.
- `credential_delete` view: soft delete instead of hard delete.
- Delete permission: switch from strict `owner != user` to the same `_can_edit` check `v5.10.1` introduced for edit (owner, or RW container access) — delete is a write operation, follows the same rule as edit.
- `create_version` signal / `CredentialVersion`: detect `is_deleted` transitions explicitly (`'deleted'`/`'restored'` labels), add `is_deleted` to `CredentialVersion`'s own snapshot fields.
- Exclude soft-deleted rows from normal visibility: `_visible_credentials`, and the `get_object_or_404` lookups in `credential_edit`/`credential_copy`/`credential_delete` (404 on an already-deleted credential).
- Import dedup check (`import_credentials`/`import_confirm`): exclude soft-deleted credentials from the "existing name" set.
- Django admin: add `is_deleted` to `list_display`/`list_filter` (visible for staff audit, not hidden).
- **Pre-existing gap fix, found during review, inherited from `v5.10.1`**: `credential_list.html` gates both the Edit and Delete buttons (desktop table + mobile cards, two separate blocks) on a plain `{% if c.owner == request.user %}` template check — never updated when `v5.10.1` introduced `_can_edit` at the view layer, so an RW container-access non-owner has been able to edit via direct URL since `v5.10.1` shipped, but never sees the button. Fixing both Edit and Delete visibility together now (same root cause, same fix). This is a conditional-visibility swap on existing buttons, not a layout/structural change, so no ASCII preview per the UI rule's intent.

# Explicit Non-Goal (verify, don't break)

`rotate_team_key`/`rotate_container_key` (`v5.10.0`/`v5.10.1`) must keep iterating over **all** credentials in scope, including soft-deleted ones — they currently have no `is_deleted` filter (the field didn't exist yet) and must stay that way. If a rotation excluded soft-deleted rows, a later restore would leave that credential's ciphertext encrypted under a discarded, unrecoverable key. No code change here, just: don't add an `is_deleted=False` filter to those two functions, and add a test case proving a soft-deleted credential's ciphertext still gets rotated correctly.

# Out of Scope

- Any "restore"/"undelete" UI or view — Django admin toggling `is_deleted` back is sufficient for now (and itself produces a "restored" changelog entry via the same signal change).
- Any change to `Container`/`ContainerAccess`/team crypto (`v5.10.0`/`v5.10.1`) — untouched.
- Cascading soft-delete when a `Team`/`Container` is deleted — separate concern, not requested.

# Technical Changes

### `vault/models.py`
- `Credential.is_deleted = models.BooleanField(default=False)`.
- `CredentialVersion.is_deleted = models.BooleanField(default=False)` (snapshot field, mirrors the other plaintext snapshot fields).

### `vault/signals.py` — `create_version`
- Add `is_deleted` to the `CredentialVersion.objects.create(...)` call (snapshot).
- Explicit transition detection, separate from the generic `_PLAINTEXT_FIELDS` loop (which would only produce a generic "is deleted" label with no direction):
  ```python
  if last and bool(last.is_deleted) != bool(instance.is_deleted):
      changed.append('deleted' if instance.is_deleted else 'restored')
  ```
- `is_deleted` is NOT added to `_PLAINTEXT_FIELDS` — handled by the explicit check above instead.

### `vault/views.py`
- `credential_delete`: replace `credential.delete()` with:
  ```python
  if not _can_edit(request.user, credential):
      raise PermissionDenied
  credential.is_deleted = True
  credential._changed_by = request.user
  credential.save(update_fields=['is_deleted'])
  ```
  (`update_fields` still triggers `post_save`/`create_version` — Django doesn't skip signals for a restricted-field save.)
- `_visible_credentials`: add `.exclude(is_deleted=True)`.
- `credential_edit`, `credential_copy`, `credential_delete`: `get_object_or_404(Credential, pk=pk)` → `get_object_or_404(Credential, pk=pk, is_deleted=False)`.
- `import_credentials`/`import_confirm`: the two `Credential.objects.filter(owner=request.user).values_list('name', flat=True)` dedup queries both add `.exclude(is_deleted=True)`.

### `vault/admin.py`
- `CredentialAdmin.list_display`: add `'is_deleted'`.
- `CredentialAdmin.list_filter`: add `'is_deleted'`.

### `vault/views.py` — `credential_list`
- Materialize `credentials` to a list and annotate each with `c.can_edit = _can_edit(request.user, c)` before rendering (templates can't call a two-arg Python function directly). Accepted simplicity tradeoff: this is N+1 queries for a list of N credentials — consistent with the rest of this small app's existing non-bulk-optimized style, not worth a bulk-annotation query for this patch.

### `vault/templates/vault/credential_list.html`
- Both the mobile-card block (~line 56) and the desktop-table block (~line 120): `{% if c.owner == request.user %}` → `{% if c.can_edit %}`, wrapping the Edit link and Delete form exactly as before — same buttons, same layout, only the visibility condition changes.

### Migration
- Standard `AddField` for both new `is_deleted` fields, `default=False` — safe, no backfill needed (all existing rows default to `False`, matching current "nothing is deleted" reality).
