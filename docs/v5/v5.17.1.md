# Goal

Add configurable **notification rules** that alert recipients when a Jira ticket matches a JSON
query, managed at `/settings/notifications/`. First use case: a new GITIN ticket that still has no
`INFRADEVOPS` tag after a grace period. Rules are generic, so more than one rule and more than
one Jira space can be covered.

# Background

- Jira does not set labels in the `jira:issue_created` event. GITIN-2268 was created at 17:45:27
  and its `labels` update arrived at 17:45:44. An alert fired at creation would be a false
  positive for any ticket tagged right after creation, so evaluation must be delayed.
- The stack has no Celery. Scheduled work runs from host cron (`jira_reconcile`, see `README.md`).
- `automations/evaluator.py::evaluate_filter` already evaluates JSON condition trees (`and`/`or`,
  JSONPath `path`, ops `eq`, `neq`, `eq_ci`, `in`, `not_in`, `in_ci`, `not_in_ci`, `contains`,
  `exists`, `regex`). It returns `False` for unknown ops and for unresolved paths.
- `notify()` already handles per-user and per-team fan-out and the system-wide
  `notifications_enabled` switch (`feature_notifications.md`).
- `NotificationsSettingsView` today holds only the on/off switch.

# Premise (rules)

1. A rule is data, not code: name, active flag, Jira filter JSON, grace minutes, message
   template, recipients (users, teams, optional "notify assignee").
2. A rule is evaluated against a payload rebuilt from the **current** `JiraTicket`, in Jira's
   shape: `issue.key`, `issue.fields.project.key`, `issue.fields.labels` (list),
   `issue.fields.status.name`, `issue.fields.assignee.accountId`, `issue.fields.summary`. It is
   never evaluated against the stored `issue_created` payload (stale labels).
3. A ticket is eligible for a rule only if: not deleted, `created_at` older than the rule's
   grace minutes, and `created_at` **after the rule's `starts_at`** (set when the rule is
   created). Existing tickets are never alerted retroactively.
4. One notification per `(rule, issue_key)`. Recorded in `NotificationRuleHit`. Later label or
   status changes do not re-notify.
5. Evaluation is delayed and periodic: a management command run from the host cron, not a
   webhook-time check.
6. Notifications go through `notify()` only, so the system-wide `notifications_enabled` switch
   gates every rule.
7. A rule with a malformed or unsupported filter is rejected on save. At run time a rule that
   fails is logged and skipped; other rules still run.

Default rule pre-filled on "New rule":

```json
{"and": [
  {"path": "$.issue.fields.project.key", "op": "eq", "value": "GITIN"},
  {"path": "$.issue.fields.labels", "op": "not_in_ci", "value": ["INFRADEVOPS"]}
]}
```

Several spaces in one rule: `{"path": "$.issue.fields.project.key", "op": "in", "value": ["GITIN", "OPS"]}`.
Different tags or recipients per space: separate rules.

# In Scope

- `notifications/models.py` (+ migration, new tables only):
  - `NotificationRule`: `name`, `is_active` (default `True`), `filter` (JSONField),
    `grace_minutes` (default `15`), `message` (CharField 500, placeholders `{key}`, `{title}`,
    `{project}`, `{status}`), `notify_assignee` (bool), `users` (M2M `User`), `teams` (M2M
    `core.Team`), `starts_at` (auto_now_add), `created_at`/`updated_at`.
  - `NotificationRuleHit`: `rule` FK (cascade), `issue_key`, `notified_at`,
    `unique_together (rule, issue_key)`.
- `notifications/rules.py` (new): payload builder from `JiraTicket`, filter-structure validator
  (valid JSON, only supported ops, every node `and`/`or`/`{path, op}`), and the evaluation
  routine used by both the command and the Test action. Reuses `evaluate_filter` without
  modifying it.
- `jira_integration/management/commands/jira_rules_check.py` (new): for every active rule, loads
  eligible tickets, evaluates, notifies via `notify()` (users, teams, assignee resolved through
  `UserProfile.jira_account_id`), writes a hit. Idempotent, safe to run every few minutes. Logs
  per-rule counts and errors. Cap of 50 notifications per rule per run.
- Notification `url`: Jira browse link when `jira_base_url` is set, else the ticket timeline.
  `source='jira_rule'`.
- `settings_hub`: `/settings/notifications/` keeps the master switch and adds a rule list, plus
  create and edit pages (`/settings/notifications/rules/new/`, `/<id>/`). Staff only. A
  "Test against ticket" action (GET `?test_key=`) shows match or no match and creates nothing.
- Templates, mobile-first: rule list as a table in `table-responsive` on desktop and
  full-width tappable cards (`d-md-none`) on mobile, with icon-only Test and active-toggle
  buttons; action bars `d-flex flex-wrap gap-2`; forms `col-12 col-md-*`.
- Docs: `.claude/feature_notifications.md` (new trigger section), `.claude/feature_settings_hub.md`
  (Notifications section), `README.md` cron line for `jira_rules_check`, the notifications docs
  section in `core/templates/core/docs.html` include if one exists.
- Tests: rule validator, payload builder, evaluation (no labels, other labels, tag present,
  case-insensitive), grace period, `starts_at` cutoff, dedupe across runs, per-rule isolation on
  error, recipients (users, teams, assignee, dedupe of a user in several), master-switch off,
  settings CRUD and Test action permissions.

# Out of Scope

- Time counting by required tag, the report warning and the required-tags setting
  (`/settings/time-report/`). Those belong to v5.17.0 and are independent.
- Extending `jira_reconcile` to backfill label history. Until then a missed label webhook is not
  recovered, and rules on projects outside `jira_reconcile_projects` rely on webhook data only.
- Hard delete of rules. Rules are deactivated with `is_active`.
- Re-notifying a ticket when it matches again later.
- Reusing or changing the automations `Trigger`/`Action` models or `evaluate_filter`.
- Email, Slack or push delivery. In-app only, as today.
- Non-Jira sources.

# Technical Changes

- Two new tables, `NotificationRule` and `NotificationRuleHit`, one migration. No existing table
  is altered, so there is no lock risk on large tables.
- `notifications/rules.py` imports `automations.evaluator.evaluate_filter`. No change to
  automations.
- New management command and a cron entry documented next to `jira_reconcile`.
- `NotificationsSettingsView` gains the rule list; new views for create, edit, toggle and test.

# Acceptance Criteria

- A new rule never alerts on tickets created before it, so the existing 88 untagged GITIN
  tickets produce no notifications.
- With the default rule, a GITIN ticket created more than the grace period ago with no
  `INFRADEVOPS` label notifies the configured recipients exactly once, however many times the
  command runs.
- A ticket tagged within the grace period never alerts.
- A ticket with `labels: []` matches `not_in_ci` and alerts.
- Two rules matching the same ticket notify independently, once each.
- A rule saved with invalid JSON, an unknown op or a malformed node is rejected and keeps the
  typed text.
- A failing rule does not stop other rules from running.
- With `notifications_enabled` off, no rule creates a notification and no hit is recorded.
- A deactivated rule creates no notifications and keeps its history.
- The Test action reports match or no match for a ticket key and writes nothing.
- `/settings/notifications/` is staff only and works at mobile width without horizontal scroll.
