# Goal

Staff-only settings page (`/settings/vault/`) for managing `Team`s and `Container`s — the UI layer on top of the crypto/permission model built in `v5.10.0`–`v5.10.4`. New card on `/settings/app/`.

# In Scope

- New card on `/settings/app/` (`app_hub.html`), matching the existing Jira/Tickets/Time Report pattern.
- `VaultSettingsView` (`settings_hub/views.py`, `StaffRequiredMixin` — same convention as every other `/settings/app/` page; cross-app settings views live in `settings_hub` even when the models belong to another app, matching `TimeReportSettingsView`'s existing precedent for `timetracking` models).
- **Teams section**: list (code, name, description, member count), inline create form (name + description; `code` auto-generated via `Team.save()`), edit (name/description/code), member management (add by username/select, remove per member).
- **Containers section**: list (name, parent, credential count), inline create form (name + parent dropdown), edit (name/parent), delete (catches `ProtectedError`, shows a friendly message naming the credential count blocking it), `ContainerAccess` grant management per container (add team + level, change level, remove grant).
- Team deletion is explicitly **not** included (deferred — needs an impact-preview UI, not a bare confirm dialog).

# Out of Scope

- Team deletion (deferred, see above).
- Tree/folder UI for browsing *credentials* — `v5.10.6`.
- KDBX import mapping to containers — `v5.10.7`.

### `settings_hub/views.py`
- Import `from core.models import Team` and `from vault.models import Container, ContainerAccess` (`Team` moved to `core` in `v5.10.4` — cross-app import, matching existing `timetracking`/`itsm`/`jira_integration` imports already in this file).
- `VaultSettingsView(StaffRequiredMixin, View)`: `get()` renders `teams` (with `.members.all()` prefetched) and `containers` (with `.access_grants.select_related('team')` and `.credentials.count()` prefetched), plus `all_users` (for the member-add dropdown) and `all_teams` (for the access-grant-add dropdown).
- `TeamCreateView`: POST — `name`/`description` required-ish (`name` required, `description` optional), `Team.objects.create(name=..., description=...)` (`code` auto-fills via `Team.save()`). Duplicate `name` → `messages.error`.
- `TeamEditView`: GET renders a form (name, description, code — all editable; `code` uniqueness re-validated on save since `Team.save()`'s auto-generation only fires when `code` is blank, an explicit edit bypasses it). POST saves.
- `TeamMemberAddView`: POST, `user_id` from a `<select>` of all `User`s not already a member. `team.members.add(user)` — existing `v5.10.0`/`v5.10.1` signals handle key wrapping automatically, no new crypto code needed here.
- `TeamMemberRemoveView`: POST. `team.members.remove(user)` — existing signals handle rotation automatically.
- `ContainerCreateView`: POST — `name` required, `parent` optional (dropdown of existing containers, empty option for root).
- `ContainerEditView`: GET/POST — name, parent. Reject setting a container as its own ancestor (walk `parent` chain, block if the new parent is `self` or a descendant — prevents an infinite loop in the tree).
- `ContainerDeleteView`: POST — `try: container.delete() except ProtectedError: messages.error(request, f'Cannot delete "{container.name}": still holds {container.credentials.count()} credential(s).')`.
- `ContainerAccessAddView`: POST — `team_id` + `access_level`. `ContainerAccess.objects.get_or_create(container=container, team=team, defaults={'access_level': access_level})` — existing `v5.10.1` `post_save` signal handles key wrapping automatically.
- `ContainerAccessLevelEditView`: POST — change `access_level` on an existing grant. No crypto action needed (confirmed in `v5.10.1`: `access_level` changes are a no-op for `ContainerKeyWrap`, view-layer-only).
- `ContainerAccessRemoveView`: POST — `.delete()`. Existing `post_delete` signal handles rotation automatically.
- All English messages via `django.contrib.messages` (matching `TimeReportSettingsView`'s convention — the legacy `Tag`/`Category` views use Spanish messages, but that predates the current English-only convention; new code follows English).

### `settings_hub/templates/settings_hub/`
- `vault_settings.html` — main page, two `section-card` blocks (Teams, Containers), following `time_report_settings.html`'s structure.
- `vault_team_form.html` — edit form, matching `tag_form.html`.
- `vault_container_form.html` — edit form, matching `category_form.html`.

### `settings_hub/templates/settings_hub/app_hub.html`
- New card: icon `bi-key`, "Vault", "Teams, containers, and sharing permissions.", badges "Teams" / "Containers", links to `settings-vault`.

# Acceptance Criteria

- [x] New "Vault" card appears on `/settings/app/`, links to `/settings/vault/`.
- [x] Staff can create a team (name + description), `code` auto-generates.
- [x] Staff can edit a team's name/description/code.
- [x] Staff can add/remove team members from the settings page — verified via real M2M state, not just a redirect. (Full crypto-signal chain — new member decrypting an existing shared credential — already proven identical to direct-ORM `team.members.add()` in `v5.10.0`/`v5.10.1`'s own tests; this view calls that exact same method, no new crypto path introduced.)
- [x] Staff can create a container (with and without a parent).
- [x] Staff can edit a container's name/parent, with cycle prevention — tested both self-parent and descendant-as-parent, both correctly rejected (200 + error, parent unchanged), not a crash.
- [x] Staff can delete an empty container; deleting one holding credentials shows a friendly error naming it's blocked, not a raw `ProtectedError` 500 (verified: `302` redirect, container still exists, error message present on reload).
- [x] Staff can add a `ContainerAccess` grant (team + level) — level applied correctly. Wrap provisioning itself confirmed **not** to fire for a brand-new container with zero credentials (correct — provisioning is lazy, only triggers on first actual encrypt/decrypt, per `v5.10.1`'s design; my first test assumed eager provisioning and was wrong, not the code).
- [x] Staff can change an existing grant's access level — verified the level actually changes.
- [x] Staff can remove a grant — verified the row is actually gone (rotation behavior itself already proven in `v5.10.1`; this view calls the same `.delete()`).
- [x] Non-staff user gets `403` — verified with a genuinely non-staff account (`no_schedule_test`; my first attempt used `agent_test`, which turns out to actually have `is_staff=True` — not a bug, a wrong test assumption, corrected).
- [x] Mobile-first: uses `col-12`/`col-md-*` responsive grids, icon-only buttons with `d-none d-md-inline` labels, matching repo conventions — code-reviewed, not visually verified in-browser at a mobile viewport.
- [x] `manage.py check` passes; full test suite (29/29) still green.
