# Goal

Fix the crash (HTTP 500) a user gets on the first visit to the time pages when they have no
`WorkSchedule` row yet.

# Background

- `WorkSchedule.start_time` / `end_time` default to the strings `'09:00'` / `'18:00'`. `get_or_create`
  returns the new instance with those strings still in memory, and the report / map code reads
  `.hour`, which raises `AttributeError: 'str' object has no attribute 'hour'`.
- Found while testing v5.20.0 (`/time/current/` for a user with no schedule row). Existing users already
  have a row, so only first visits fail. Five call sites use `get_or_create`.

# Premise (rules)

1. Fix at the source: the model defaults become real `datetime.time` values (09:00 and 18:00), so every
   call site is fixed at once. Stored data and the database defaults are unchanged.

# In Scope

- `timetracking/models.py` defaults, migration `0007_workschedule_time_defaults` (state change only,
  no table rewrite), tests for a user without a schedule on the report, the map, the entry list and
  the user settings page (where the schedule form lives; `/time/schedule/` redirects there).

# Out of Scope

- Any other behaviour of the time pages; v5.21.0 (tag report).

# Technical Changes

- Two `AlterField` operations that only change the Python-side default.

# Acceptance Criteria

- A user with no `WorkSchedule` row gets 200 on `/time/current/`, `/time/map/`, `/time/` and the
  user settings page; the created row has `09:00` and `18:00` as times.

# Related Scope Dependencies
