# Goal

Two related fixes to `vault/forms.py`'s `CredentialForm`, sharing the same root fix (encrypt against the credential's *actual* boundary, not blindly against whoever's editing):

1. **Bug fix**: `CredentialForm.save()` currently always encrypts `password`/`private_key`/`passphrase` changes with `encrypt_for_user(self.user, ...)` — the *editing user's* personal key — regardless of whether the credential is container- or team-shared. Rotating a secret on any shared credential silently re-encrypts it with the wrong key, breaking decryption for everyone else.
2. **New feature**: `Credential.notes` becomes encrypted (currently plaintext) with its own independent visibility toggle (`notes_shared`), separate from the secret's sharing scope — sharing a credential's password must never automatically expose its notes.

# In Scope

- New `crypto.py` helpers: `encrypt_for_credential(credential, acting_user, plaintext)` / `decrypt_for_credential(credential, acting_user, token)` — resolve the boundary (container → legacy team → personal owner-key) once, used for `password`/`private_key`/`passphrase`. Refactor `credential_copy`'s existing branch logic to use `decrypt_for_credential` instead of duplicating the container/team/owner branching inline.
- `CredentialForm.save()`: use `encrypt_for_credential` instead of `encrypt_for_user` for the three secret fields.
- `Credential.encrypted_notes` (replaces plaintext `notes`), `Credential.notes_shared = BooleanField(default=False)`.
- New `crypto.py` helpers: `encrypt_notes_for_credential(credential, acting_user, plaintext)` / `decrypt_notes_for_credential(...)` — `notes_shared=True` and a container exists → container-key; otherwise → `credential.owner`'s personal key. Independent of how the secret itself is encrypted.
- **Only the owner can toggle `notes_shared` or read/write notes when it's `False`.** A non-owner RW container member sees notes only when `notes_shared=True` (re-encrypted with the container key at that point); the toggle itself is owner-only in the form. Read-only (R) container members still can't reach the edit form at all — unchanged, no new view page (see resolved design decision below).
- `CredentialVersion`: `notes` moves from the plaintext-snapshot group to the ciphertext-snapshot group (`encrypted_notes`, stored as-is like the other secret snapshots) — also removed from `_PLAINTEXT_FIELDS` diffing (comparing ciphertext directly would false-positive "notes changed" on every save, since Fernet tokens are non-deterministic even for identical plaintext).
- Migration: encrypt existing plaintext `notes` with the owner's personal key (`notes_shared` defaults to `False`, so this is the correct default boundary for every existing row).

# Out of Scope (resolved design decision)

- Extending notes visibility to read-only (R) container members — would require a new read-only credential detail/view page (none exists today; `credential_form.html` is the only place notes render, gated by `_can_edit`). Likely overlaps with the tree UI work (`v5.10.5`). Not building it now.
- `/settings/app/` team & container management UI — `v5.10.4`.
- Re-encrypting historical `CredentialVersion` notes snapshots on a `notes_shared` toggle — same accepted limitation as the existing secret-snapshot handling (nothing in the UI ever decrypts version history).
- **Known limitation**: for a legacy team credential (`visibility='team'`, no `container`), `notes_shared=True` has no visible effect — `decrypt_notes_for_credential`/`encrypt_notes_for_credential` only route to the container path, never the legacy team path. Toggling it on such a credential silently changes nothing observable (notes stay owner-key-only). Not fixed here — legacy team credentials are transitional/shrinking (superseded by containers since `v5.10.1`), not worth a third encryption path for. Flagged so it isn't mistaken for a bug later.

# Technical Changes

### `vault/crypto.py`
- `encrypt_for_credential(credential, acting_user, plaintext)` / `decrypt_for_credential(credential, acting_user, token)`:
  ```python
  def _resolve_credential_boundary(credential):
      if credential.container_id:
          return ('container', credential.container)
      if credential.visibility == Credential.VIS_TEAM and credential.team_id:
          return ('team', credential.team)
      return ('personal', credential.owner)
  ```
  then dispatch to `encrypt_for_container`/`encrypt_for_team`/`encrypt_for_user` (and decrypt equivalents) accordingly. `acting_user` is used for the container/team paths (needed to resolve *their* key wrap); the personal path always uses `credential.owner` regardless of `acting_user` (matches existing `decrypt_for_user(credential.owner, ...)` usage in `credential_copy`).
- `encrypt_notes_for_credential`/`decrypt_notes_for_credential`: `if credential.notes_shared and credential.container_id: → encrypt_for_container/decrypt_for_container(credential.container, acting_user, ...)`, `else: → encrypt_for_user/decrypt_for_user(credential.owner, ...)`.
- Neither pair does permission checking — same convention as existing `decrypt_for_container`/`decrypt_for_team`/`decrypt_for_user`. Permission gating (who's even allowed to call these) stays in `views.py`/`forms.py`, matching the existing pattern.

### `vault/views.py`
- `credential_copy`: replace the inline `if credential.container_id / elif owner / else` branch with a single `decrypt_for_credential(credential, request.user, token)` call.
- `credential_edit`: compute `can_see_notes = (request.user == credential.owner) or (credential.notes_shared and _can_edit(request.user, credential))` (note: this evaluates to owner-or-notes-shared-RW, since `_can_edit` is already gated to owner-or-RW at the top of the view — the `notes_shared` check only matters for the *non-owner* RW case). Pass to the form as `show_notes=can_see_notes`, `can_toggle_notes_shared=(request.user == credential.owner)`.

### `vault/forms.py` — `CredentialForm`
- Remove `'notes'` from `Meta.fields` (no longer a direct plaintext passthrough) — model field is now `encrypted_notes`, ciphertext.
- Add non-model fields: `notes = forms.CharField(required=False, widget=forms.Textarea(attrs={'rows': 3}))`, `notes_shared = forms.BooleanField(required=False, label='Share notes with team (readable/editable by read-write members)')`.
- `__init__(self, *args, user=None, show_notes=True, can_toggle_notes_shared=True, **kwargs)`: if `self.instance.pk` and `show_notes`, decrypt via `decrypt_notes_for_credential(self.instance, user, self.instance.encrypted_notes)` into `self.fields['notes'].initial`; if not `show_notes`, disable the `notes` field (`disabled=True`, empty) with a placeholder like "Notes are private to the owner." If not `can_toggle_notes_shared`, disable the `notes_shared` field too (rendered but not submittable).
- `save()`: use `encrypt_for_credential` for the three secret fields (bug fix). For notes: capture the *original* decrypted text and *original* `notes_shared` value at `__init__` time (both needed for the comparison below, not just the text). Re-encrypt (`instance.encrypted_notes = encrypt_notes_for_credential(instance, self.user, self.cleaned_data['notes'])`) if `show_notes` was `True` for this form instance (a non-owner without notes visibility must never blank out or overwrite notes they can't see) **and** (the submitted text differs from the original decrypted text **or** `notes_shared` differs from its original value) — toggling the share flag alone, with no text edit, must still re-encrypt, since the boundary key changes independent of the text. Uses the *new* `instance.notes_shared` (post-form-save) to pick the boundary, so a toggle takes effect in the same save.

### `vault/models.py`
- `Credential.notes` (`TextField(blank=True)`) → removed. New: `Credential.encrypted_notes = models.TextField(blank=True)`, `Credential.notes_shared = models.BooleanField(default=False)`.
- `CredentialVersion.notes` → `CredentialVersion.encrypted_notes` (ciphertext snapshot, moved next to `encrypted_password` etc.). Add `CredentialVersion.notes_shared = models.BooleanField(default=False)` (plaintext snapshot, safe — it's just a flag, not a secret).

### `vault/signals.py` — `create_version`
- Remove `'notes'` from `_PLAINTEXT_FIELDS`.
- Add `'encrypted_notes'` to `_SECRET_LABELS` (label: `'notes changed'`) — same ciphertext-equality comparison pattern as the other secret fields, correct now since notes only gets re-encrypted when actually changed (see form `save()` above), not on every save.
- Add `notes_shared` to the plaintext-style diff (own explicit check, like `is_deleted`'s `'deleted'`/`'restored'` pattern): `if last and bool(last.notes_shared) != bool(instance.notes_shared): changed.append('notes shared' if instance.notes_shared else 'notes unshared')`.
- `CredentialVersion.objects.create(...)`: add `encrypted_notes=instance.encrypted_notes`, `notes_shared=instance.notes_shared`; remove the old `notes=instance.notes` line.

### Migration
- `RemoveField(Credential.notes)` is destructive if done naively — instead: `AddField(encrypted_notes, blank=True, default='')`, `AddField(notes_shared, default=False)`, `RunPython` encrypting existing plaintext `notes` values (`encrypt_for_user(credential.owner, credential.notes)`) into `encrypted_notes` via `.update()`, *then* `RemoveField(Credential.notes)` — all as one migration, in that order, so the plaintext is never dropped before being captured.
- Same shape for `CredentialVersion`: `AddField(encrypted_notes)`, `AddField(notes_shared, default=False)`, `RunPython` encrypting each version row's plaintext `notes` (using that version's `credential.owner` — the *current* owner, since historical versions don't track a per-version owner), `RemoveField(CredentialVersion.notes)`.

# Delivery Note

Two migration-state mistakes hit while writing the `notes` → `encrypted_notes` data migration, both classic "historical vs. live model" traps:

1. The `RunPython` function initially imported `from vault.models import Credential, CredentialVersion` (the *live* models) for its query. But by the time this migration runs, `models.py` has already been edited to remove `notes` entirely — the live `Credential` model doesn't have that field anymore, so `Credential.objects.exclude(notes='')` raised `FieldError: Cannot resolve keyword 'notes'`. Fixed by using `apps.get_model('vault', 'Credential')` instead — the historical migration-state model, which still has both `notes` and `encrypted_notes` at this specific point in the migration graph.

2. Fixing #1 exposed a second issue: `credential.owner` from an `apps.get_model` historical instance is a *different class* than the live `django.contrib.auth.models.User` that `UserVaultKey.user` (used by the live-imported `encrypt_for_user`) expects — `ValueError: Cannot query "User object (1)": Must be "User" instance`. Fixed by re-fetching the owner live: `User.objects.get(pk=credential.owner_id)` (importing `django.contrib.auth.models.User` directly, which is standard practice in migrations since Django's own `auth` app model shape is stable enough not to need `apps.get_model` for this kind of usage).

General lesson for future Vault migrations that mix `RunPython` data transforms with the real `crypto.py` functions: query via `apps.get_model` for whichever model's shape changed in this migration, but re-fetch any *foreign* live model (like `User`) by primary key before passing it into a live-imported crypto function — don't pass historical-model FK objects across that boundary.

Also repeated the `v5.10.0`/`v5.10.1` entrypoint-auto-migrate race: ran `docker compose up --build -d app` (which triggers the container's own `migrate --noinput` on startup) immediately followed by an explicit `docker compose run --entrypoint python app manage.py migrate vault`, and the two raced — one produced a `DuplicateColumn` error, but the *other* had already completed the migration successfully underneath it. Confirmed via `django_migrations`/`\d` that the migration did actually apply cleanly and no data was lost; the error was cosmetic noise from the losing process, not a real failure. Lesson holds from before: don't run an explicit `migrate` right after `up -d` when the image was just rebuilt with new migrations — let the container's own entrypoint handle it, or use `docker compose stop app` first.
