# Goal

Fix the "Today" hours shown in the In Progress panel's parent/child envelope
(`/time/report/`) when a parent ticket and its child are both In Progress at overlapping
times — currently the combined total naively **sums** each ticket's own duration, which
roughly doubles the real elapsed time whenever their In Progress windows overlap (the common
case, since moving a subtask to In Progress often auto-transitions its parent too).

# Background

Reported via `GITIN-1637` (parent) / `GITIN-2102` (child), both assigned to the same user:

- `1637` entered In Progress at `14:28:59`, still ongoing → **1h48m** own duration.
- `2102` entered In Progress at `14:29:30` (31s later), still ongoing → **1h47m** own duration.
- The envelope header combines them as `1h48m + 1h47m ≈ 3h35m` — but the two windows are
  almost entirely the same wall-clock time, so the real combined elapsed time is ~1h48m, not
  3h35m.

# In Scope

- `timetracking/views.py`, `DailyReportView.get`, the envelope-combine block (~lines 786-794):
  replace the naive `_parent_row['_ongoing_secs'] + row['_ongoing_secs']` /
  `_parent_row['_today_secs'] + row['_today_secs']` sums with a proper **union of time
  intervals** between the parent's and child's qualifying segments — the same
  merge-overlapping-intervals approach already used for the In Progress bar chart
  (`raw_ip`/`merged_ip`, ~lines 1146-1169), scoped to this one parent/child pair instead of
  all tickets.
  - `jira_today`: union of both tickets' In-Progress segments clipped to `[today_start, now]`.
  - `jira_ongoing`: union of both tickets' currently-open segments (each running to `now`) —
    equivalent to `now − earliest of the two entered_at` when both are ongoing.
- Applies only to the **single parent + single child** case that already exists in this code
  path (one envelope header combining one parent row with one child row).

# Out of Scope

- A parent with **multiple concurrently In Progress children**: today's code renders one
  envelope per child, each independently combining with the parent — so the parent's own time
  gets pulled into every such envelope rather than being split/deduplicated across them. This
  is a distinct, more involved restructuring (grouping all IP children of a parent into a
  single envelope) and is not touched here since it wasn't the reported issue and no such case
  is live in current data. Flagged as a known limitation, not fixed in this patch.
- Any other panel (Gantt, Status History pivot, Time by Status, Time by Environment/Project).
- Changing how standalone (non-enveloped) tickets compute their own `jira_ongoing`/`jira_today`
  — those are unaffected, already correct.

# Technical Changes

- `timetracking/views.py`: add a small local `_union_secs(intervals)` helper (merge overlapping
  `(start, end)` tuples, sum covered duration) near the envelope-combine block; rewrite the
  `row['parent_row']` construction to build interval lists from both tickets'
  `ticket_segments` entries and pass them through `_union_secs()` instead of summing precomputed
  totals.

# Acceptance Criteria

- For `GITIN-1637`/`GITIN-2102` (or any parent/child pair with overlapping In Progress windows),
  the envelope's combined `jira_ongoing`/`jira_today` equals the true elapsed wall-clock union,
  not the sum of the two tickets' individual durations.
- A parent/child pair with **non-overlapping** In Progress windows (e.g. parent was IP
  yesterday, child IP today, no overlap) still shows the correct combined total — union math
  falls back to sum when intervals don't overlap, so this case is unaffected.
- Standalone (non-enveloped) rows are pixel/value-identical to before this change.

# Addendum: Time by Environment color-palette bug (found while testing this branch)

Reported: with `SmartPedidos`/`SmartLoyalty`/`SmartCloud` selected, the donut only showed 2
visually distinct sections and no real colors. Root cause: `envColorFor()` (then `ENV_COLOR`)
indexed the 8-hue categorical palette by each tag's **alphabetical position among all of
`tag_totals`** — which is shared across the whole report (Project + Environment + plain Jira
status-name tags) and held 65 distinct entries in this install. Real environment tags landed
at index 51-53, past the 8-slot palette, so all three silently fell back to the same gray.

**Fix** (`timetracking/templates/timetracking/report.html`): color is now a **stable hash of
the tag's own name** mod 8 (`envColorFor()`), independent of the surrounding tag pool size or
the current selection. Two tag names can still collide into the same slot (accepted trade-off
of a fixed 8-hue palette — never generate a 9th hue), but this no longer depends on how many
unrelated tags exist system-wide.

Bundled into this branch rather than a separate patch since it was found live while testing
`v5.15.1` and touches the same card/file.

# Addendum 2: "Today" boundary used UTC midnight instead of the viewer's local midnight

Reported: on `/time/report/?range=week`, the In Progress panel's "Today" figure looked wrong
("that's UTC").

Root cause (`timetracking/views.py:733`): `today_start = now.replace(hour=0, minute=0,
second=0, microsecond=0)` zeroed the clock fields on the raw UTC-aware `now`, producing UTC
midnight — while the range boundaries (`start_dt` for today/week/month, lines 255-259) correctly
compute local midnight via `now_local.replace(...).astimezone(UTC)` first. For any
`WorkSchedule.timezone` offset from UTC, this shifted the "today" window by that offset,
misattributing segments near the boundary to the wrong calendar day.

**Fix**: `today_start` now uses the same `now_local.replace(...).astimezone(UTC)` pattern as
`start_dt`. This is the same `today_start` the child-priority envelope fix above (Addendum
none, main scope) already reads, so no further change was needed there.

Bundled here for the same reason as the color-palette addendum.
