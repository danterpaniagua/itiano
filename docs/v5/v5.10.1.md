# Goal

Introduce `Container` as a hierarchical, KeePass-style grouping for credentials, with per-team read/read-write access grants (`ContainerAccess`) — the actual crypto/data-model layer needed for "Operations team = RW, Devs team = R on the same set of credentials." Backend and data model only; no new UI beyond query changes to existing views (tree UI is `v5.10.3`, settings management UI is `v5.10.2`).

**Resolved design decision**: the *Container* is the encryption boundary, not the Team (v5.10.0's `TeamKeyWrap` stays as-is for now, unused by new code going forward). A new `ContainerKeyWrap(container, user)` follows the exact same wrap/rotate pattern as `TeamKeyWrap`, but membership is derived dynamically — every member of *every* team with *any* (`read` or `read_write`) `ContainerAccess` grant on a container gets a key wrap, so they can all decrypt. The read/read-write distinction is enforced entirely at the application layer (blocks *saving* changes), never by withholding the decryption key — this matches how Bitwarden/KeePass-style tools actually work, and is the only way one container can serve multiple teams at different access levels.

# In Scope

- `Container` model: `name`, `parent` (self FK, nullable, `on_delete=CASCADE`), `created_by` (FK User, nullable, `SET_NULL`), `created_at`.
- `ContainerAccess` model: `container` FK CASCADE, `team` FK CASCADE, `access_level` (`read`/`read_write`), `unique_together=[('container','team')]`.
- `ContainerKeyWrap` model: same shape as `TeamKeyWrap` (`container`, `user`, `wrapped_key`, `created_at`, `unique_together=[('container','user')]`).
- `Credential.container` FK (nullable, blank, `on_delete=PROTECT` — a container with credentials in it cannot be deleted, preventing orphaned unwrappable ciphertext).
- `crypto.py`: `get_container_members`, `provision_container_key`, `wrap_container_key_for_user`, `get_container_fernet`, `encrypt_for_container`, `decrypt_for_container`, `rotate_container_key` — parallel to v5.10.0's team functions.
- Signal cascade keeping `ContainerKeyWrap` in sync with true membership (see Technical Changes) across three triggers: `Team.members` changes, `ContainerAccess` creation, `ContainerAccess` deletion. Must correctly handle a user who has access via *two* teams on the same container (removing one shouldn't revoke access).
- Data migration: for each `Team` with existing `visibility='team'` credentials, auto-create a `Container` (named after the team), grant that team `read_write` via `ContainerAccess`, re-encrypt those credentials' secrets from team-key (v5.10.0) to container-key, set `credential.container`. **`credential.team`/`credential.visibility` fields are left untouched** — not removed, not repurposed. Full retirement of those fields is deferred to whenever the tree UI (`v5.10.3`) fully replaces them as the navigation model.
- `vault/views.py`:
  - `_can_access` / `_visible_credentials`: extended to also include container-granted access (any level) — otherwise a second team granted read-only access via a *new* `ContainerAccess` (not the legacy single `team` FK) would never see the credential in their list at all.
  - `credential_copy`: prefer `decrypt_for_container` when `credential.container` is set; fall back to the v5.10.0 team-key path (defensive, shouldn't be hit post-migration) or owner-key path as before.
  - `credential_edit`: replace the current hard `owner != user → PermissionDenied` with a `_can_edit` check — owner, or a member of a team with `read_write` `ContainerAccess` on the credential's container.

# Out of Scope

- Any new template/page — `/settings/app/` team & container management UI is `v5.10.2`.
- Notes independent-visibility toggle — `v5.10.2`.
- Tree/folder UI, search — `v5.10.3`.
- KDBX merge import — `v5.10.4`.
- Retiring `Credential.team`/`Credential.visibility` — deferred, see above.
- Per-credential access overrides (only container-level grants exist) — not requested.

# Technical Changes

### `vault/models.py`
- `Container(name, parent FK→self CASCADE null/blank, created_by FK→User SET_NULL null/blank, created_at)`.
- `ContainerAccess(container FK CASCADE, team FK CASCADE, access_level CharField choices=[read, read_write] default=read)`, `unique_together=[('container','team')]`.
- `ContainerKeyWrap(container FK CASCADE related_name='key_wraps', user FK CASCADE, wrapped_key TextField, created_at)`, `unique_together=[('container','user')]`.
- `Credential.container = models.ForeignKey(Container, on_delete=models.PROTECT, null=True, blank=True, related_name='credentials')`.

### `vault/crypto.py`
- `get_container_members(container)`: `User.objects.filter(vault_teams__in=ContainerAccess.objects.filter(container=container).values('team')).distinct()`, unioned with `container.created_by` if set.
- `provision_container_key`, `wrap_container_key_for_user`, `get_container_fernet`, `encrypt_for_container`, `decrypt_for_container`: direct copies of the v5.10.0 team-keyed functions, retargeted to `Container`/`ContainerKeyWrap`.
- `rotate_container_key(container, excluded_users=None)`: same shape as `rotate_team_key`, re-encrypts `Credential.objects.filter(container=container)` instead of filtering by `team`+`visibility`.

### `vault/signals.py` — the hard part
- **`Team.members` `m2m_changed` (extends the v5.10.0 handler)**:
  - `post_add`: for each `ContainerAccess(team=instance)` → `container`, for each added user without an existing `ContainerKeyWrap(container, user)`, call `wrap_container_key_for_user`.
  - `pre_remove`: for each `ContainerAccess(team=instance)` → `container`, compute `truly_excluded` = removed users who have **no other** `ContainerAccess`-granted team (excluding `instance`) that they still belong to for this same `container`. Only call `rotate_container_key(container, excluded_users=truly_excluded)` if `truly_excluded` is non-empty.
- **New `post_save` receiver on `ContainerAccess`** (`created=True` only): for each member of the newly-granted `team`, if they lack a `ContainerKeyWrap` for this `container`, `wrap_container_key_for_user`.
- **New `post_delete` receiver on `ContainerAccess`**: for each member of the just-revoked `team`, check if they still have access via any *remaining* `ContainerAccess` grant on this `container` (query `ContainerAccess.objects.filter(container=instance.container, team__members=member).exists()`); those who don't → `rotate_container_key(container, excluded_users=[...])`.
- Helper `_user_has_other_container_access(container, user, excluding_team_id)` shared by both the `Team.members` and `ContainerAccess` paths to avoid duplicating this overlap-check logic.

### Migration (`vault/migrations/0005_...`)
- Schema: `CreateModel(Container)`, `CreateModel(ContainerAccess)`, `CreateModel(ContainerKeyWrap)`, `AddField(Credential.container)`.
- Data (`RunPython`): for each `Team` with `Credential.objects.filter(team=t, visibility='team').exists()`: create `Container(name=t.name, created_by=None)`, create `ContainerAccess(container=c, team=t, access_level='read_write')`, then for each such credential, decrypt via v5.10.0's `decrypt_for_team(t, credential.owner, token)` and re-encrypt via `encrypt_for_container(c, credential.owner, plaintext)` for each non-blank secret field, `.update()` the row plus `container_id`. Irreversible (same reasoning as v5.10.0's migration).
- **Defensive per-credential handling**: `decrypt_for_team` assumes `credential.owner` currently holds a `TeamKeyWrap` for `t` (i.e., is still a team member) — nothing enforces an owner stays on the team after creating a team credential. Wrap each credential's re-encryption step in its own try/except; on failure, `print`/log a warning identifying the credential and skip it (leave it un-migrated, `container` stays `None`) rather than aborting the whole migration for every remaining credential in the batch.

### `vault/views.py`
- `_can_access`: add `Q(container__access_grants__team__members=user)` alongside the existing owner/team checks.
- `_visible_credentials`: same additional `Q`.
- `credential_copy`: branch order becomes owner → container (if `credential.container_id`) → legacy team (fallback) → deny.
- `credential_edit`: new `_can_edit(user, credential)` — owner, or `ContainerAccess.objects.filter(container=credential.container, team__members=user, access_level='read_write').exists()`.

# Delivery Note

Two real bugs found and fixed during implementation, neither caught by design review alone:

1. **`Team.code` collision on any second `Team` created without an explicit `code`.** `v5.10.0` added `code` as `unique=True, blank=True` but only backfilled *existing* rows in its migration — nothing auto-generates `code` for newly-created `Team` rows going forward. The very first attempt to smoke-test this scope (creating two disposable teams) hit `IntegrityError: duplicate key ... code=()`. Fixed by adding a `Team.save()` override that auto-slugifies `name` into `code` when blank, with the same collision-disambiguation suffix logic as the `v5.10.0` migration's backfill. This would have broken the `v5.10.2` settings UI (team creation) the moment two teams were created without manually setting a code.

2. **`Team.delete()` silently failed to revoke container access for members who only had access through that team.** The original design tracked "who was just removed" via the `m2m_changed` signal's `pk_set`/`pre_remove`/`post_delete` payloads. But `m2m_changed` does **not** fire when M2M rows are cleared as a side effect of cascade-deleting a related object — `Team.delete()` cascades `ContainerAccess` and `Team_members` rows directly via SQL, bypassing the M2M signal machinery entirely. The `ContainerAccess.post_delete` handler then read `instance.team.members.all()` to figure out who to exclude, but by that point the `Team_members` rows were already gone (cascade-deleted in the same operation, order not guaranteed relative to `ContainerAccess`), so it saw an empty set and did nothing — access silently stayed valid for a user whose only path to it had just been deleted.

   Fixed by replacing all "track who was removed via signal payload" logic for containers with a single `reconcile_container_access(container)` primitive (`crypto.py`) that always recomputes valid membership from current `ContainerAccess` grants (`get_container_members`) and diffs it against current `ContainerKeyWrap` holders — wrapping the missing, rotating out the stale. This is invoked uniformly from `Team.members` `post_add`/`post_remove` (not `pre_remove` — the reconciliation needs the membership row to already be gone, unlike the exclusion-list-based `rotate_team_key` which works at either timing) and from `ContainerAccess` `post_save`/`post_delete`. Caught and fixed only because the `Team.delete()` cascade case was explicitly in the Validation Plan (added during the pre-implementation review) rather than assumed to work by analogy with the `Team.members.remove()` case.

3. **`credential_copy` failed for the owner of a container-based credential** (found retroactively, during `v5.10.2` work, while testing with real accounts — `ope_test`/`agent_test` — instead of synthetic role permutations). The view branched on `if credential.owner == request.user` *before* checking `credential.container_id`, so an owner accessing their own container-based credential took the `decrypt_for_user` path (personal key) even though the secret was actually encrypted via `encrypt_for_container` (container key) — raising `cryptography.fernet.InvalidToken`. Every `v5.10.1`/`v5.10.2` test up to this point happened to use a *non-owner* as the acting user for `credential_copy`, so this never surfaced. Fixed by reordering the branches to check `container_id` first — encryption routing must follow *how the secret was actually encrypted*, not *who's asking*. Fixed in `vault/views.py` on the `v5.10.2` branch; flagged here since the bug originates in this scope's code. Verified via the real HTTP view as both `ope_test` (owner, RW) and `agent_test` (non-owner, R) — both now correctly decrypt.
