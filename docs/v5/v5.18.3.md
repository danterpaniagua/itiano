# Goal

Count the in-range part of **In Progress (IP) stays that began before the range**, in every time
panel, so the report no longer drops time worked across midnight (or across a week or month
start). This scope merges the former v5.18.2 (tag totals ignoring a still-open pre-range stay)
and the "began before, ended inside the range" case into one rule.

# Background

- Reported Oct 30 2026. GITIN-2315 (`[SP] Node 20->22 upgrade`) and its child GITIN-2318 entered
  IP on Oct 29 at 17:18 Córdoba. 2318 closed today at 12:00:11, 2315 is still open.
- `range_bounds()` in `DailyReportView.get` counts a pre-range segment only when it is still
  ongoing; every other pre-range segment contributes 0 ("all other pre-range segments contribute
  0"). Consequences today, Exclusive mode:
  - GITIN-2318 (began before, ended inside): 0 in every panel, about 11h 39m 35s wall-clock or
    3h 39m 35s in working hours (W-H) lost.
  - GITIN-2315 (still open): counted from `start_dt` in the pivot, status totals and Today panel,
    but 0 in Time by Project / Time by Environment, whose tag totals block keeps its own filter
    `entered_at >= start_dt` ("ongoing IP from before the range contributes 0 here").
- With the fix, the pieces of the day add up to 13h 16m 00s (00:00 to 13:16), and 5h 16m 00s in
  W-H (08:00 to 13:16). Tags `SmartPedidos`, `Concentrador`, `INFRADEVOPS`, `SRE` stop showing
  nearly nothing.
- Tag timing is not part of this. `TicketTag` has no timestamp and attributes a ticket's whole IP
  time to all its current tags; late tagging was checked and does not hide any time here. The
  "count only from tag assignment" idea (v5.17.0) stays parked.

# Premise (rules)

1. **IP stays.** An IP segment overlapping the range counts for `[max(entered_at, start_dt),
   min(exited_at or now, now)]`. This covers began-before-and-ongoing, and
   began-before-and-ended-inside. A segment that ended before `start_dt`, or a zero or negative
   window, counts 0.
2. **Non-IP statuses unchanged.** Blocked, Testing, Backlog and other statuses keep the current
   rule (entered inside the range, or ongoing for the IP-only flag). They would otherwise inflate
   Time by Status. (Assumed from the recommendation; confirm.)
3. **Exclusive mode.** The measured window goes through `excl_secs()` (owned slices), with the
   existing Labor clipping. The slices are already built over the full history, so a stay that
   began before the range is already known.
4. **Overlap mode.** The same window, wall-clock or Labor-clipped, per ticket, with one
   exception for the tag totals: a parent gets only the time it was IP while none of its
   same-user children was (`union(parent + children) - union(children)`, the Today panel
   envelope rule), so a parent and its subtask are not counted twice. Children keep their own
   time; siblings are not merged. (Decided with the user after seeing SmartPedidos at 9h 29m.)
5. **One rule everywhere.** Pivot, status totals, closed tickets, Today panel and the tag totals
   (Time by Project / Time by Environment, All and Labor) use the same IP window, so a ticket has
   the same time in all of them.
6. **Tags unchanged.** `TicketTag` attribution, tag filter, status filter and the per-card pill
   selection behave as today.

# Added during implementation (approved by the user)

- **Carried-over stays restart at the first working hour.** A stay that began before a local day
  and is still running through it does not count that day's hours before the schedule's first
  working hour; a non-working day counts nothing for it. Evening hours after the end of the
  schedule still count (so past totals stay stable). Same-day entries count from their entry.
  Wall-clock only; Labor is unchanged. Applied to the pivot / status totals / closed tickets, the
  tag totals and the Today panel's "today" figure. Not applied to the Today panel "ongoing"
  total, IP bar, Gantt or the map card times. This replaces the earlier rule that counted a
  carried-over stay from the start of the range (00:00): GITIN-2318 on Oct 30 is 3h 39m 35s, not
  11h 39m 35s.

- **Exclusive is the default Time mode** (you can only work on one task at a time). `?time=overlap`
  is now the opt-in param, carried by the range/tag/status forms and filter links; exclusive
  carries nothing. Global for every user; a per-user setting is a possible follow-up.
- Overlap tag totals count a parent and its subtask once (rule 4).

# Technical Changes

- Two small local helpers (interval merge, interval seconds) in the tag-totals block, a
  per-ticket window map and a parent-to-children map built from `my_tickets`.
- One helper and two call sites in `DailyReportView.get`. No models, no migrations, no new
  queries; `ticket_segments` already carries every segment.
- Expected effect on existing numbers: only stays that began before the range start change.
  Totals can go up in Week/Month and in Today after midnight work.

# Acceptance Criteria

- Exclusive, Today, with the Oct 30 data: GITIN-2318 shows 3h 39m 35s wall-clock and
  3h 39m 35s Labor (it restarts at 08:00, the first working hour); GITIN-2315 keeps its time from
  12:00:11 and now also counts in the tag totals.
- `INFRADEVOPS`/`SRE` totals equal the sum of the ticket pieces, with no double counting; the
  00:00-08:00 stretch has no owner.
- A stay carried over from the previous day does not count before the first working hour, and
  counts nothing on a non-working day; a same-day entry counts from its entry; Labor is unchanged.
- A stay that ended before the range starts counts 0 in every panel.
- A stay that straddles the range start counts only its in-range part (Week and Month included).
- When a newer IP ticket takes focus, the older one's time stops while paused (slices, not
  re-implemented).
- Pivot, Today panel and tag totals show the same value for the same ticket.
- Overlap mode changes only where a stay straddled the range start, or where a parent and its
  subtask were IP at the same time (counted once).
- Parent 08:00-12:00 with a subtask 09:00-11:00 and the same tag: 4h total (6h before), and
  3h in Labor with a 09:00-18:00 schedule, in both modes.
- Non-IP rows in Time by Status are unchanged.
