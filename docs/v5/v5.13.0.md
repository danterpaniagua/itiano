# Goal

Add a generic in-app notification system: a `notify()` helper other apps can call to alert
either a single user or every current member of a `core.Team`. Surfaced via a bell/dropdown in
the navbar and a full notifications list page. Wired to two triggers on delivery: vault
team-sharing, and `jira_reconcile` run completion.

# In Scope

- New `notifications` app:
  - `Notification` model — one row per recipient: `user` (FK), `message` (CharField), `url`
    (CharField, blank, optional deep link), `source` (CharField, e.g. `vault_share`,
    `jira_reconcile`), `created_at` (auto_now_add), `read_at` (nullable DateTimeField).
  - `notify(message, *, url='', source='', users=None, team=None)` — accepts either an iterable
    of `User` / a single `User` via `users`, or a `core.Team` via `team` (resolved to
    `team.members.all()` at call time, i.e. a snapshot of current membership). Exactly one of
    `users`/`team` must be given.
  - Navbar bell partial (unread count badge, recent N notifications, mark-as-read per item,
    mark-all-read) injected into `core/templates/base.html`.
  - Full "My Notifications" page (`/notifications/`) listing all of the current user's
    notifications, newest first (no pagination in this version — add one if volume grows).
  - Context processor exposing unread count + recent list to every template (mirrors
    `core.context_processors.app_version`).
  - Dashboard card (unread count, links to `/notifications/`).
  - `notifications/templates/notifications/docs.html` + tab in `core/templates/core/docs.html`.
  - `.claude/feature_notifications.md` — living reference doc for the feature.
- Vault trigger: hook into the credential/container team-sharing code paths in `vault/views.py`
  (wherever `visibility='team'` is set on a `Credential`, and wherever a `ContainerAccess` grant
  is created) to call `notify(..., team=<that team>)`.
- `settings_hub` addition: a multi-user field on the existing Settings → Jira page
  (`settings-jira`), backed by `AppSetting` key `jira_reconcile_notify_users` (comma-separated
  usernames, same storage pattern as the existing `jira_reconcile_projects` setting). Empty by
  default (no recipients configured = no notification sent).
- `jira_reconcile` trigger: at the end of `Command.handle()`, after computing `stats`, call
  `notify(...)` targeting the users configured in `jira_reconcile_notify_users`:
  - `by_time` mode message: `f"jira_reconcile by_time: Updated: {stats['events_created']}"`.
  - `last` mode message: `f"jira_reconcile last: Created {stats['tickets_created']} Updated {stats['events_created']}"`.
  - No notification sent if `jira_reconcile_notify_users` is empty, or if `issues_scanned == 0`.

# Out of Scope

- Real-time push (websockets/polling) — unread state refreshes on normal page navigation only.
- Email/Slack/webhook delivery — no `EMAIL_BACKEND` configured in this app today; a future scope
  if wanted.
- Per-user notification preferences or muting.
- Retroactive notifications for shares or reconcile runs that already happened before this ships.
- Any change to `jira_reconcile`'s reconciliation logic itself (already shipped on this branch).

# Acceptance Criteria

- Sharing a credential or granting a container to a team creates one `Notification` per current
  team member; each sees it in their bell/list independently and can mark it read without
  affecting other recipients.
- Configuring `jira_reconcile_notify_users` in Settings → Jira, then running
  `jira_reconcile by_time` or `jira_reconcile last [N]`, creates one `Notification` per
  configured recipient with the correct message format for that verb.
- No `jira_reconcile_notify_users` configured → command runs exactly as before, no notification
  attempted, no error.
- Bell badge count and dropdown, and the full `/notifications/` page, all render correctly per
  the Mobile-First UI Rules (table-responsive/card layouts N/A here, but dropdown and list must
  work without horizontal scroll on mobile).
- Dashboard card, docs tab, and `feature_notifications.md` all present per New App Delivery
  Requirements.

# Validation Plan

- `docker compose exec app python manage.py test notifications vault jira_integration
  settings_hub core` — **run, 40 tests, OK** (28 pre-existing `jira_integration` + 12 new
  `notifications`; `vault`/`settings_hub`/`core` contribute 0, no `tests.py` in those apps yet).
- Manual (via `docker compose exec app python manage.py shell` + Django test `Client`, against
  the real Postgres container): `notify()` team fan-out, single-user, empty-list no-op, and the
  `ValueError` on neither/both of `users`/`team` — all confirmed. `/notifications/` list,
  open-and-mark-read redirect, mark-all-read (scoped to the current user only), dashboard card,
  docs tab, and the Settings → Jira recipients field (render + POST persistence) — all confirmed
  via real HTTP requests, not just unit assertions. `jira_reconcile`'s `_notify_completion` for
  both verbs, and the no-recipients-configured no-op — confirmed with real message content.
- `vault/signals.py::handle_container_access_created` — exercised directly (real
  `ContainerAccess.objects.create()` against Postgres): 2 notifications on grant creation, 0 on
  a subsequent `access_level` edit of the same grant (confirms the `created=True` gate).
- `vault/views.py::_notify_credential_shared` and the `credential_edit` gating condition
  (`newly_team_shared`) — exercised directly against real `Credential` rows: create-time share
  notifies both team members with the expected message; an unrelated edit to an already
  team-shared credential does not re-notify; a personal→team edit does. (The full encrypted
  `CredentialForm`/crypto-envelope flow itself — team key wraps, PBKDF2 provisioning — was not
  driven end-to-end here; that flow is pre-existing and unrelated to this scope's changes.)
- Not exercised: an actual browser walkthrough of the bell dropdown UI.
