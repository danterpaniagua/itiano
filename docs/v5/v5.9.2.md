# Goal

Fix the Time by Status trend indicator (v5.9.0) so it doesn't display absurd percentages (e.g. `▲ 10572389%`) when the previous equivalent-range baseline is statistically insignificant — a few seconds of working time from a brief status flicker in the prior window.

# In Scope

- New global setting `trend_min_baseline_seconds` (default `300`), editable at `/settings/time-report/` alongside `stuck_threshold_hours`, following the exact same `AppSetting` pattern.
- Trend calculation in `timetracking/views.py` (~line 579-588): when `prev_secs` is below `trend_min_baseline_seconds`, treat it the same as `prev_secs == 0` — show `new` instead of a percentage — rather than only guarding against exactly zero.
- Applies uniformly to `today`/`week`/`month`/`custom` ranges (same shared calculation).

# Out of Scope

- Any redesign of the trend feature's UX (arrow, color, wording) — approved and delivered in v5.9.0.
- Changing how `prev_status_working_seconds` / `_prev_window_bounds` select segments — not touching *why* the previous window can be near-zero, only guarding the *display* of the ratio.
- The negative-percentage direction — `trend_pct` is mathematically bounded at -100% when `current < prev`, so no explosion is possible there; not treated as a bug.
- Reconciling the already-committed-but-unrecorded `v5.9.1` (Time by Tag removal) into `versions.md`/`VERSION` — separate, untouched concern.

# Technical Changes

### `settings_hub/views.py` — `TimeReportSettingsView`
- `_ctx()`: add `'trend_min_baseline_seconds': get_app_setting('trend_min_baseline_seconds', '300')`.
- `post()`: add `elif action == 'set_trend_min_baseline':` branch — parse `int(value)`, validate `>= 0`, on error `messages.error(...)`, on success `AppSetting.objects.update_or_create(key='trend_min_baseline_seconds', defaults={'value': str(seconds)})` + `messages.success(...)`.

### `settings_hub/templates/settings_hub/time_report_settings.html`
- New `section-card` form block mirroring the existing `stuck_threshold_hours` block: hidden `action=set_trend_min_baseline` input, `type="number"` input named `trend_min_baseline_seconds`, `value="{{ trend_min_baseline_seconds }}"`, `min="0" step="1" required`, Save button.

### `timetracking/views.py`
- Read the setting near the existing `_stuck_threshold_hours` read (~line 628-634), same try/except-cast pattern: `_trend_min_baseline_secs = 300` → `try: _trend_min_baseline_secs = float(get_app_setting('trend_min_baseline_seconds', '300')) except (TypeError, ValueError): pass`.
- In the trend loop (~line 579-588), change the guard from `if prev_secs > 0:` to `if prev_secs > _trend_min_baseline_secs:`; the `else` branch (already sets `trend_pct = None`, `trend_new = True`) is unchanged and now also covers the "tiny but nonzero" case.
