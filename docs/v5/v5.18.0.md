# Goal

Add an **In Progress map** card to `/time/report/` that shows, for the selected range (Today /
Week / Month / custom From–To), how many times tickets were put into In Progress (IP) and in what
order, as per-day chains of ticket cards: `Ticket A → Ticket B → Ticket C`. Each card shows how the
IP entry started (origin) and where the ticket went when it left IP (destination). A copy-only
Mermaid export of the same data is available for docs and tickets.

# Background

- The report shows IP *time* (IP bar, Today panel, pivot, tag totals) but not the *sequence* of
  work: which tickets were picked up, in what order, and how each stay ended.
- Real data (Oct 1–29 2026, one user): 77 IP entries over 57 tickets after collapsing parent
  auto-transitions. Destinations: 38 done, 33 blocked, 5 queue, 1 still IP. Origins: 55 first-ever
  entries, 16 resumed from blocked, 4 from queue, 2 reopened from done.
- Jira sometimes records `In Progress → En curso` (localized duplicate, same category). A naive
  "next status" shows a false still-IP destination, so entries and destinations are decided by
  status **category** (`JiraStatusConfig`), not by name.
- Moving a child to IP commonly auto-transitions its parent too (documented in v5.15.1), so a raw
  chain would list the parent right next to the child for a single action.
- Ticket tags: `TicketTag` is polluted with status names (`Bloqueado`, `Done`, `In Progress`) and
  `auto-infradevops`; `JiraTicket.labels` is clean.
- Approved mockup: `docs/mockup/mockup_ip_map.html` (local file, fake data).

# Premise (rules)

1. **Entry.** A status transition whose `toString` is in the `in_progress` category and whose
   previous status is not in that category. A transition between two IP-category names (e.g.
   `In Progress → En curso`) is the same stay, not a new entry. Only tickets of the viewer
   (`my_tickets`, same matching as the rest of the report) take part.
2. **Range.** An entry belongs to the range if its `received_at` falls inside it. Days are
   grouped in the viewer's `WorkSchedule.timezone`. Entries are ordered by `received_at`.
3. **Origin.** `Created` for the ticket's first-ever IP entry (full history, not just the range).
   Otherwise the category of the previous status: blocked, testing, queue (backlog/other) or
   done (reopened).
4. **Destination.** The first following status outside the in_progress category. No such status
   = still IP now.
5. **Parent collapse.** An entry of a parent is dropped when one of its children (same user, via
   `parent_key`) enters IP within 60 seconds of it, in either order. A parent entry with no such
   child stays.
6. **Re-entries.** A ticket that returns later gets its own card. Consecutive entries of the same
   ticket are one card with a `×N` badge.
7. **Counts.** The header shows entries and distinct tickets, plus the per-destination breakdown.
8. **Independent of the Time toggle.** The map is based on status entries and does not change
   with `Overlap | Exclusive` or `All | Labor` (it counts events, not time).
9. **Filters.** The report's tag filter applies (only tickets that pass it are mapped). The
   status filter does not (it filters by activity status, not by IP entries). Confirm against the
   existing filter code during implementation.

# In Scope

- `timetracking/ip_map.py` (new, pure functions, no DB access): builds the per-day entries from
  the per-ticket status transitions, `JiraStatusConfig` categories, `parent_key` data and the
  viewer timezone, applying rules 1–7. Also builds the Mermaid text.
- `timetracking/views.py`, `DailyReportView.get`: reuses the transitions already fetched for
  `ticket_segments` (no extra query per ticket where possible), calls the helper for the active
  range and passes `ip_map_days`, `ip_map_summary` and `ip_map_mermaid` to the template.
- `timetracking/templates/timetracking/report.html`: new card below the IP bar.
  - Summary line: entries · tickets · destination counts, plus a legend of the icons.
  - Per day: heading with date and entry count, then cards in chain order.
  - Card: ticket ID as the link (to `/time/report/ticket/<key>/timeline/`) with a small `↗` Jira
    link when `jira_base_url` is set, origin → destination icons right-aligned (tooltips with the
    exact status names and time spent in IP), 2-line clamped title, tags from
    `JiraTicket.labels`.
  - Tags: 3 badges + `+N` on desktop, 2 badges + `+N` on mobile; the rest in the badge title.
  - Desktop (md and up): fixed-width cards, wrapping, `→` connector after every card except the
    last of the day. Mobile: full-width stacked cards, no connectors, days with more than 4 cards
    show 4 and a "Show N more / Show less" button (fixed threshold).
  - "Copy as Mermaid" button that copies the text of all days in the range (clipboard only, text
    emitted by the server in a `<script type="text/plain">` block). No Mermaid library, no
    rendering, no new dependency.
  - Empty state when the range has no IP entries.
- Mobile-first rules from `CLAUDE.md` apply: action bar `d-flex flex-wrap gap-2`, no horizontal
  scroll, no hidden buttons.
- Tests in `timetracking` for the helper and the view (see Validation Plan).
- Docs: `.claude/feature_timetracking_report.md` and the Time Report section in
  `timetracking/templates/timetracking/docs.html`.

# Out of Scope

- A `+N` trail badge listing the statuses between the destination and the next IP entry (the
  destination stays the first non-IP status). Candidate follow-up.
- An Exclusive-aware map that follows ownership handoffs instead of raw entries. The map ignores
  the Time toggle in this version.
- Rendering Mermaid in the page or adding any diagram library. Export is copy-only text.
- Click-to-filter on an icon, per-card expansion, drag or zoom.
- A separate "Created" step for the literal creation event (`Created` here means the first IP
  entry).
- Tags from `TicketTag`, tag history, or label-change history.
- Tickets no longer assigned to the user (existing `my_tickets` limitation) and other users'
  maps.
- Changes to the IP bar, Gantt, Today panel, pivot, status totals or any time calculation.
- The required-tag time rule and the report warning (v5.17.0, not written) and anything in
  `jira_reconcile`.

# Technical Changes

- New module `timetracking/ip_map.py`; the view calls it. No new models and no migrations.
- No change to how `ticket_segments`, `excl_slices` or any existing total is computed.
- `report.html` gets the card, a small inline script for the mobile "Show more" toggle and the
  clipboard copy, and CSS for the card layout (no new static files).

# Acceptance Criteria

- For the same user and range, entry counts and distinct-ticket counts match the helper's output
  exactly; with the real October data at the time of writing (Oct 1–29) the card shows 77 entries
  and 57 tickets, destinations 38 / 33 / 5 / 1 and origins 55 / 16 / 4 / 2.
- An `In Progress → En curso` transition never creates a second entry or a false still-IP.
- A parent that enters IP within 60 seconds of its child does not appear; a parent without such a
  child does.
- A ticket's first-ever IP entry is `Created` even when it happened before the range; later
  entries use the previous status category.
- A ticket that returns later in the day appears again; consecutive entries of the same ticket
  appear once with `×N`.
- Entries are grouped by day in the viewer's timezone, around midnight included, and ordered by
  `received_at`.
- The tag filter limits the mapped tickets; the Time toggle and Labor toggle do not change the
  map.
- The ticket ID links to the ticket timeline; the Jira link shows only when `jira_base_url` is
  set.
- With a day of more than 4 cards, mobile shows 4 plus a working "Show N more" button; desktop
  shows all.
- "Copy as Mermaid" puts valid `flowchart LR` text for every day in the range on the clipboard
  and loads no external script.
- No other panel changes with the card added; an empty range shows the empty state.
- The card works at mobile width without horizontal scroll.
