# Goal

The Jira integration is 100% webhook-driven. When the app is down (deploy, crash,
maintenance window), Jira does not retry failed webhook delivery indefinitely, so
affected tickets end up with permanent gaps in their `JiraEvent` history — status
timelines and reports silently go stale for those tickets.

Add a scheduled reconciliation job that polls the Jira REST API and backfills any
status transitions missing from `JiraEvent`, so outages no longer produce permanent
data loss.

# In Scope

- New management command `jira_integration/management/commands/jira_reconcile.py`:
  - Reads a watermark timestamp from `AppSetting` (settings_hub), defaulting to
    "24 hours ago" on first run.
  - Queries Jira with JQL `updated >= "<watermark>" ORDER BY updated ASC` via
    `GET /rest/api/3/search/jql` (the classic `/rest/api/3/search` endpoint is
    deprecated and returns 410 Gone; the enhanced endpoint paginates via
    `nextPageToken`, not `startAt`/`total`) to list candidate issues.
  - Scan scope is restricted to specific Jira project(s) via
    `AND project in (...)` in the JQL, read from `AppSetting` key
    `jira_reconcile_projects` (comma-separated project keys). Defaults to
    `GITIN` when unset.
- Jira Settings page (`settings_hub`, `settings-jira` view/template) gets a new
  "Reconcile Projects" text field (comma-separated project keys), saved to the
  same `AppSetting` key, next to the existing Base URL field.
- App-wide logging fix: `LOGGING['formatters']['standard']` in `config/settings.py`
  silently dropped every `extra={}` field passed to `logger.info/warning/exception`
  across the whole app — the format string never referenced them. Added
  `config/logging_formatters.py:ExtraFormatter`, which appends any non-standard
  `LogRecord` attributes as `key=value` pairs. This was required for the
  reconcile command's per-ticket outcome logging to actually be visible.
- `jira_reconcile` now logs one `jira_reconcile_issue_done` line per known
  ticket scanned (not just when something changed), with
  `outcome=updated|unchanged` and `events_created=N`.
  - For each issue, fetches `GET /rest/api/3/issue/{key}?expand=changelog`
    (paginated changelog if needed).
  - Walks changelog `histories[]`, filters items where `field == "status"`.
  - For each such history entry, checks whether a `JiraEvent` already exists for
    that ticket carrying that Jira `history.id` (see dedup key below). If missing,
    creates a `JiraEvent` with `event_type='jira:issue_updated'` and
    `received_at` set to the changelog history's real `created` timestamp — never
    "now".
  - Never writes `JiraTicket` fields from live snapshot data. Status changes are
    derived exclusively from changelog items, consistent with the webhook path
    (`jira_integration/views.py:webhook`) and the rule in
    `.claude/feature_jira_workflow.md`.
  - On success, advances the `AppSetting` watermark to the run's start time (not
    "now", to avoid a race with issues updated mid-run).
  - Structured logging per run: issues scanned, events backfilled, errors,
    duration — following the existing `logger.info(..., extra={...})` pattern
    used in `jira_integration/views.py`.
  - Handles Jira API pagination and 429 rate-limit responses with backoff.
- Dedup key: store Jira's changelog `history.id` in `JiraEvent.payload` (e.g.
  `payload['history_id']`) for both webhook-created and crawler-created events,
  and use it to detect "already captured." Webhook events also get this field
  populated retroactively is NOT required — dedup only needs to work going
  forward once this ships (see Migration Notes below for the fallback used on
  pre-existing events).
- Migration: `JiraEvent.received_at` changes from `auto_now_add=True` to a plain
  `DateTimeField(default=django.utils.timezone.now)`. Existing rows keep their
  current values; only future inserts (webhook or crawler) can now set it
  explicitly. Webhook path (`views.py`) is updated to pass `received_at` from the
  webhook `payload.get('timestamp')` when present, else `timezone.now()`.
- New env vars: `JIRA_API_BASE_URL`, `JIRA_API_EMAIL`, `JIRA_API_TOKEN` (Basic
  Auth against Jira Cloud REST API v3), added to `.env.example` and referenced
  via `settings.py` / `django.conf.settings`.
- README: document the cron entry to run
  `python manage.py jira_reconcile` hourly (host cron, no Celery).
- Tests: `jira_integration/tests.py` — dedup logic (no double-insert for a
  history already captured by the webhook), watermark advancement, and that
  reconciliation never overwrites `JiraTicket` fields from snapshot data.

# Out of Scope

- Vault-based credential storage for the Jira API token. Deferred — Vault's
  envelope encryption is keyed to a logged-in user's wrapped key, and a headless
  cron job has no session. Using Vault here would require a new service-account
  decrypt path that doesn't exist yet. → tracked as
  `.claude/deferred_vault_service_credentials.md` if we want to revisit later.
- Celery, Celery Beat, or any new scheduler/broker dependency.
- Backfilling non-status changelog fields (assignee, labels, parent, etc.
  history) — only status transitions are reconciled, since that's what drives
  the status-timeline and report logic.
- Retroactively populating `history_id` on pre-existing `JiraEvent` rows created
  before this ships.
- Any UI/dashboard for reconciliation run history — visibility is via logs and
  the existing `JiraEvent`/`JiraTicket` Django admin.
- Reconciling gaps older than the configured watermark lookback on first run
  (24h) unless explicitly re-run with a manually adjusted `AppSetting` value.

# Acceptance Criteria

- Running `python manage.py jira_reconcile` with a valid Jira token backfills
  any status-changing `JiraEvent` missing since the watermark, without touching
  tickets/events already correctly recorded by the webhook.
- Running it twice in a row produces zero duplicate `JiraEvent` rows (idempotent).
- A ticket whose only status history came from the crawler (e.g. simulating a
  full webhook outage) produces the same status timeline
  (`_build_status_timeline` in `views.py`) as if the webhook had received the
  events live.
- `JiraTicket.status`/other fields are never overwritten by live snapshot values
  during reconciliation — only by changelog `toString` values, matching the
  webhook rule.
- The watermark in `AppSetting` advances only after a fully successful run; a
  failed/partial run does not advance it (so the next run retries the same
  window).
- Command logs are structured and informative enough to diagnose a failed run
  from `docker compose logs`.
- All existing `jira_integration` tests still pass.

# Validation Plan

- New unit tests in `jira_integration/tests.py` covering: dedup by
  `history_id`, watermark advancement/non-advancement on failure, changelog
  parsing, and status-timeline equivalence between webhook-sourced and
  crawler-sourced events.
- Manual test: executed against the real Jira instance
  (`smartit-ar.atlassian.net`) — scanned 84 issues, backfilled 17 missing
  status-transition events, 0 errors, watermark advanced. Uncovered and fixed
  a real-world issue: `/rest/api/3/search` is deprecated (410 Gone); switched
  to `/rest/api/3/search/jql` with `nextPageToken` pagination.
- Full suite: `docker compose exec app python manage.py test jira_integration`
  — executed, 23/23 passed.
