# Goal

Give `Team`s a shared encryption key so any member can decrypt a team credential's secret directly, instead of only the credential's owner being able to (current state: `vault/views.py` `credential_copy` hard-requires `credential.owner == user`). This is the crypto foundation the rest of the Vault team-sharing work (`v5.10.1`–`v5.10.3`) depends on. Promotes `.claude/deferred_team_credentials_shared_key.md`.

Notes stay out of this entirely — `Credential.notes` keeps its current plaintext/owner-scoped handling. Only the three secret fields (`encrypted_password`, `encrypted_private_key`, `encrypted_passphrase`) move to team-key encryption when `visibility='team'`.

# In Scope

- `Team` model gets two new fields: `code` (short technical identifier, e.g. `ope`, `sml_dev` — unique, slug-like) and `description` (free text). Existing `name` field is unchanged in meaning — stays the human-readable label (e.g. "Operaciones"). No UI to set these yet (team creation/editing UI is `v5.10.1`); this is schema-only, done now to avoid a second migration later.
- New `TeamKeyWrap` model: one row per `(team, user)`, storing the team's Fernet data-key wrapped with that user's personal Fernet (`get_user_fernet`), so only current members can unwrap it.
- `crypto.py` additions: `get_team_fernet(team, acting_user)`, `encrypt_for_team(team, acting_user, plaintext)`, `decrypt_for_team(team, acting_user, token)`, `provision_team_key(team)` (lazy — creates the team's key + wraps for current members on first use), `wrap_team_key_for_user(team, user)`, `rotate_team_key(team, excluded_user=None)`.
- `m2m_changed` signal on `Team.members.through` (new receiver in `vault/signals.py`, following the existing `post_save`/`create_version` pattern):
  - `post_add`: wrap the existing team key for newly-added members (no-op if the team has no key yet — provisioned lazily on first encrypt).
  - `pre_remove`: rotate the team's key (new key, re-encrypt all that team's credentials, re-wrap for remaining members, drop the removed member's wrap).
- Data migration: existing `visibility='team'` credentials get their three secret fields re-encrypted from the owner's personal key to the team's key. Uses `.update()` (not `.save()`) to avoid firing the `CredentialVersion` snapshot signal.
- `vault/views.py` `credential_copy`: team members (not just the owner) can decrypt a team credential's secret via `decrypt_for_team`.

# Out of Scope

- `Container`/`ContainerAccess` model, per-team read vs. read-write distinction (today it's all-or-nothing team membership) — `v5.10.1`.
- Notes independent-visibility toggle — `v5.10.1`.
- Tree UI, search — `v5.10.2`.
- KDBX merge import — `v5.10.3`.
- Re-encrypting historical `CredentialVersion` secret snapshots on rotation — confirmed nothing in the UI ever decrypts version-history secrets (`credential_form.html` only shows `changed_fields` labels like "password changed", never the value), so old version rows become permanently undecryptable after a rotation. Accepted limitation, not fixed here.
- `m2m_changed` `pre_clear`/`post_clear` (removing all members at once) — deliberately left unhandled. Rotating to zero remaining members would orphan the just-rotated ciphertext on next access (provisioning would silently generate yet another key, permanently losing the rotated one) — worse than a no-op. Existing wraps are simply left in place until this edge case gets a real design.

# Technical Changes

### `vault/models.py`
- `Team`: add `code = models.SlugField(max_length=50, blank=True, default='')` and `description = models.TextField(blank=True, default='')`. `code` is tightened to `unique=True` in the same migration after backfill (see Migration below) — not declared unique directly in the model diff to avoid a broken intermediate state.
- New `TeamKeyWrap(team FK→Team CASCADE related_name='key_wraps', user FK→User CASCADE related_name='team_key_wraps', wrapped_key TextField, created_at auto_now_add)`, `unique_together = [('team', 'user')]`.

### `vault/crypto.py`
- `provision_team_key(team)`: `Fernet.generate_key()`, wrap for every current `team.members.all()` via `wrap_team_key_for_user`. Called lazily by `get_team_fernet`/`encrypt_for_team` when `TeamKeyWrap.objects.filter(team=team).exists()` is `False`.
- `wrap_team_key_for_user(team, user)`: requires an existing wrap to already exist for *some* member (to unwrap the current raw team key) — assert `TeamKeyWrap.objects.filter(team=team).exists()` before calling directly (provisioning is the only path that creates the first wrap).
- `get_team_fernet(team, acting_user)`: look up `TeamKeyWrap(team, acting_user)`; if missing, provision (if team has zero wraps at all) or raise `PermissionError` (team has a key but this user has no wrap — not a current member). Decrypt `wrapped_key` via `get_user_fernet(acting_user)`.
- `encrypt_for_team`/`decrypt_for_team`: thin wrappers over `get_team_fernet(...).encrypt/decrypt`, empty-string short-circuit matching `encrypt_for_user`/`decrypt_for_user`.
- `rotate_team_key(team, excluded_users=None)`: `excluded_users` is an iterable (not a single user) so a bulk member-removal fires exactly one rotation, not one per removed user. Generate new key; for each `Credential` where `team=team, visibility='team'`, decrypt each non-blank secret field with the *old* team fernet (obtained via any wrap not belonging to an excluded user, captured before rotation) and re-encrypt with the new key, `.update()` on the queryset row-by-row; delete all existing `TeamKeyWrap` rows for the team; re-wrap the new key for `team.members.exclude(pk__in=excluded_ids)`.

### `vault/signals.py`
- New `m2m_changed` receiver, `sender=Team.members.through`:
  - `action == 'post_add'`: for each `pk` in `pk_set`, if `TeamKeyWrap.objects.filter(team=instance).exists()`, call `wrap_team_key_for_user(instance, User.objects.get(pk=pk))`.
  - `action == 'pre_remove'`: call `rotate_team_key(instance, excluded_users=User.objects.filter(pk__in=pk_set))` once for the whole batch — must run in `pre_remove` (not `post_remove`) so "remaining members" can still be computed correctly relative to the M2M state (the removal hasn't committed yet at this point).

### `vault/apps.py`
- No change needed — `ready()` already imports `vault.signals`, new receiver registers automatically.

### Migration (`vault/migrations/0004_...`)
- Schema: `AddField(Team.code, blank=True, default='')`, `AddField(Team.description, blank=True, default='')`, create `TeamKeyWrap`.
- Data (`RunPython`): backfill `code` for every existing `Team` row via `slugify(name)`, disambiguating collisions with a numeric suffix (`ope`, `ope-2`, ...).
- Schema: `AlterField(Team.code, unique=True)` — safe at this point since backfill guarantees uniqueness. All three steps live in one migration file, in this order.
- Data (`RunPython`): for each `Team` with `credentials.filter(visibility='team').exists()`: iterate its team credentials, for each non-blank secret field, `plaintext = decrypt_for_user(credential.owner, old_value)` then `new_value = encrypt_for_team(credential.team, credential.owner, plaintext)`, `Credential.objects.filter(pk=credential.pk).update(**{field: new_value})`. Reverse migration: no-op (documented as irreversible — re-encrypting back to owner-key would require the team key surviving a rollback, which schema reversal would have already deleted).

### `vault/views.py`
- `credential_copy` (~line 87-100): branch — if `credential.owner == user`: `decrypt_for_user` (unchanged, personal credentials). Elif `credential.visibility == 'team' and credential.team and _can_access(user, credential)`: `decrypt_for_team(credential.team, user, ...)`. Else: `PermissionDenied` (unchanged).

# Delivery Note

Hit and fixed a genuine Django migration bug while applying this: the original migration split `Team.code` into `AddField(blank=True, default='')` → backfill → `AlterField(unique=True)` to safely add a unique field to a table with existing rows. But `SlugField` defaults to `db_index=True`, so the initial `AddField` queued a *deferred* index-creation SQL statement (Django defers non-critical `db_index` SQL to the end of the migration's transaction). The later `AlterField(unique=True)` step creates its own same-named `_like` index immediately as part of enforcing uniqueness. When the deferred SQL from the first step finally flushed at the end of the transaction, it collided with the index the second step had already created — `relation "vault_team_code_a10057ad_like" already exists`. Fixed by adding `db_index=False` explicitly on the initial `AddField`, so only the final `AlterField` creates the index. Also discovered along the way: `entrypoint.sh` always runs `migrate --noinput` on container start regardless of any command override passed to `docker compose run` (it doesn't `exec "$@"`) — use `--entrypoint python` to bypass it when you need to run one-off management commands without triggering a full migrate+gunicorn cycle.
