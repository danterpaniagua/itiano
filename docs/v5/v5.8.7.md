# v5.8.7 — Timezone Setting per User (WorkSchedule)

## Goal

Add a `timezone` field to `WorkSchedule` so that `start_time` / `end_time` are interpreted in the user's local timezone when compared against UTC event timestamps from Jira webhooks. This is a data-model prerequisite for v5.9.0 (Working Hours Mode).

## In Scope

- Add `timezone = CharField(max_length=64, default='UTC')` to `WorkSchedule`
- Migration (additive, safe on any table size)
- Expose `timezone` in the schedule settings form with a text input (free-form IANA timezone string, e.g. `America/New_York`)
- Show the field in `schedule.html`

## Out of Scope

- Applying timezone conversion logic anywhere (belongs in v5.9.0)
- Per-user timezone for dashboard timestamps, ticket display, or any other context
- A dropdown of all IANA timezones (text input is sufficient for now)
- Timezone validation beyond Django form `clean()` using `zoneinfo.ZoneInfoNotFoundError`

## Technical Changes

- `timetracking/models.py`: add `timezone` field to `WorkSchedule`
- `timetracking/migrations/`: new migration
- `timetracking/forms.py`: add `timezone` to `WorkScheduleForm`
- `timetracking/templates/timetracking/schedule.html`: render the new field

## Acceptance Criteria

- `WorkSchedule` has a `timezone` field defaulting to `'UTC'`
- Existing schedules are unaffected (default preserves current behavior)
- User can save a valid IANA timezone string (e.g. `Europe/Madrid`) via the settings form
- Invalid timezone strings are rejected with a form validation error

## Validation Plan

- Open `/time/schedule/`, verify `timezone` field is present with default `UTC`
- Save `Europe/Madrid` — confirm it persists
- Save `Not/ATimezone` — confirm form error is shown

## Dependencies

- No dependencies. v5.9.0 depends on this scope.
