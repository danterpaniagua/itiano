# Goal

Make three previously-hardcoded behaviors configurable: a system-wide on/off switch for all
notifications (covering both v5.13.0 triggers), and two `jira_reconcile` tuning defaults
(watermark lookback hours, and the `last` verb's default issue count).

# In Scope

- `notifications_enabled` `AppSetting` (`'True'`/`'False'`, default enabled) — checked once
  inside `notify()` itself, so it gates every current and future trigger without each call site
  needing its own copy of the check. New Settings page `settings-notifications`
  (`/settings/notifications/`, staff only), linked from the App Settings hub.
- `jira_reconcile_lookback_hours` `AppSetting` (default `24`) — replaces the hardcoded
  `DEFAULT_LOOKBACK_HOURS` used by `_get_watermark()` on a first run (no watermark saved yet).
- `jira_reconcile_last_count` `AppSetting` (default `300`) — replaces the hardcoded
  `DEFAULT_LAST_COUNT` used when `jira_reconcile last` is invoked without an explicit count. An
  explicit CLI count still overrides it.
- Both new `jira_reconcile` fields added to the existing Settings → Jira page, alongside
  `jira_reconcile_projects` / `jira_reconcile_notify_users`.
- Both numeric settings are read defensively (`Command._get_int_setting`): an unset, non-numeric,
  or non-positive value falls back to the hardcoded constant rather than crashing the command —
  this matters because `jira_reconcile` runs unattended via cron.

# Out of Scope

- Per-source override of the notifications toggle (e.g. "vault on, jira off") — one switch only,
  as requested.
- Any change to `jira_reconcile`'s reconciliation logic itself, or to the notification message
  formats — already shipped in v5.13.0.
- Validating `jira_reconcile_projects`' project keys actually exist in Jira — unrelated,
  pre-existing behavior, not touched here.

# Technical Changes

- `notifications/models.py`: `ENABLED_KEY` constant; `notify()` checks it (after argument
  validation, before resolving recipients) and returns `[]` early when disabled.
- `settings_hub/views.py`: new `NotificationsSettingsView`; `JiraSettingsView._ctx()` +
  `post()` gain the two new fields (`reconcile_defaults_form` POST marker, matching the existing
  per-form-marker convention on that page); both validated server-side as positive integers
  (invalid input shows an error message and leaves the stored value unchanged, rather than saving
  garbage that would silently trigger the command-side fallback).
- `settings_hub/urls.py`: `settings-notifications` route.
- `settings_hub/templates/settings_hub/notifications_settings.html`: new.
- `settings_hub/templates/settings_hub/jira_settings.html`: new "Reconcile Defaults" section.
- `settings_hub/templates/settings_hub/app_hub.html`: new "Notifications" card.
- `jira_integration/management/commands/jira_reconcile.py`: `LOOKBACK_HOURS_KEY`,
  `LAST_COUNT_KEY` constants; `_get_int_setting()` helper; `count` CLI arg now defaults to `None`
  (resolved from settings in `handle()`) instead of the constant directly; `_get_watermark()`
  reads the configured lookback instead of the constant.
- `.claude/feature_notifications.md`, `.claude/feature_jira_workflow.md`: updated.

# Acceptance Criteria

- Toggling `notifications_enabled` off makes `notify()` a no-op for both the vault-share and
  `jira_reconcile` triggers (and any future caller) — confirmed via `notify()` unit tests and a
  `jira_reconcile` integration test with the setting off.
- `jira_reconcile last` with no count uses the configured `jira_reconcile_last_count`; an explicit
  CLI count still overrides it; an invalid/unset setting falls back to `300`.
- `jira_reconcile`'s first-ever watermark uses the configured `jira_reconcile_lookback_hours`; an
  invalid/zero/unset setting falls back to `24`.
- Settings → Jira → "Reconcile Defaults" and Settings → App Settings → "Notifications" render and
  persist correctly, reject non-numeric/non-positive input without crashing or corrupting the
  stored value.
